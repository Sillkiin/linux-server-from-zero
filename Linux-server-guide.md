# Linux-сервер с нуля

Подробная инструкция для новичка, знакомого с Windows. Подготовлена 15 ноября 2026 года.

Сервер — обычный компьютер, который постоянно выполняет задачи для других. На него добавляют программы, разрешают им доступ к файлам и сети, включают их как службы и следят за результатом.

Команды разобраны для Ubuntu Server 24.04 LTS с systemd. Это выбранная учебная версия, а не утверждение о самой новой версии Ubuntu. В Debian многие действия похожи; в AlmaLinux, Rocky Linux, RHEL, Astra Linux и ALT отличаются пакеты, службы и правила безопасности.

## Как пользоваться

Интерактивная версия — Linux-server.html. Открой её в Edge, Chrome, Safari или Firefox. Для автономного HTML интернет не нужен. Настоящие команды выполняй отдельно, в своей учебной Linux-ВМ. Терминал страницы — симуляция.

Начни с одной отдельной виртуальной машины. Перед изменением существующего файла сохрани его копию и права. Вводи команды по строке и проверяй результат перед продолжением. В карточках отличай команды, конфигурационные файлы и код программы.

192.0.2.0/24 и 203.0.113.0/24 — документационные адреса. Имена *.example.test — учебные. Они не описывают твою сеть; замени их реальными значениями, когда разбираешь свою ВМ.

## Перед первой командой

### Где мы занимаемся

Учебник открыт в браузере. Его сцены, тесты и терминал — модель. Для настоящих команд нужна отдельная учебная виртуальная машина с Ubuntu Server 24.04 LTS. ВМ — отдельный виртуальный компьютер внутри твоего Windows-компьютера.

### Как различать два терминала

PowerShell на Windows обычно показывает приглашение PS C:\…>. После входа по SSH приглашение меняется примерно на student@linux-lab:~$. Это уже команды Linux на сервере. Сами PS, путь и знак $ из приглашения переписывать не надо.

### Как вводить команды

Вводи одну строку, нажимай Enter и читай ответ. Перенос длинной строки на экране не создаёт вторую команду. Не вставляй сразу всю карточку, если первая строка просит пароль, подтверждение или сообщает ошибку.

### Что делать, когда спрашивают пароль

При вводе пароля в Linux символы и звёздочки обычно не видны. Это нормально: введи пароль и нажми Enter. sudo обычно спрашивает пароль твоего Linux-пользователя. После [Y/n] Y означает согласие, n — отказ.

### Команда и содержимое файла

Тёмный блок может содержать команду, код программы или текст настройки. У каждой карточки теперь есть явный тип. YAML, server {…} и [Service] вставляют в указанный файл через редактор; напрямую в терминале их не выполняют.

### Как сохранить файл

В nano: Ctrl+O (латинская буква O, не цифра 0) → Enter → Ctrl+X. Первые два действия сохраняют, последнее закрывает редактор. Для существующих системных настроек сначала нужна отдельная копия. Карточка файла показывает команду открытия.

### Какие значения заменить

student — пример имени: используй своё. 192.0.2.10 — пример адреса ВМ; enp1s0 — пример интерфейса. Адреса 192.0.2.* и имена .test используются для объяснений и не описывают твою сеть. anna, project, labdb и hello — имена новых учебных объектов; их оставляем одинаковыми во всех связанных упражнениях.

### Как понять, что получилось

Команда может успешно завершиться без текста. Но это ещё не проверка всей задачи. Читай «Как проверить»: нужна своя страница, новый вход, созданный файл или возвращённая запись. Если видишь ошибку, остановись на этой строке и разбери её.

### Если nano не найден

В терминале учебной Ubuntu выполни по строке:

```bash
sudo apt update
sudo apt install nano
```

### Символы в командах

- `-h, --help` — Параметры команды: меняют поведение программы. Короткий параметр обычно начинается с одного дефиса, длинный — с двух.
- `sudo apt install nginx` — sudo — с административными правами; apt — менеджер пакетов; install — установить; nginx — название пакета.
- `~ и /` — ~ — твоя домашняя папка. / в начале пути — корень файловой системы. /etc/nginx — абсолютный путь, он не зависит от текущей папки.
- `|` — Передать текстовый вывод одной команды другой. Это не буква I. Например, sshd -T | grep … оставляет в длинном выводе нужные строки.
- `> и >>` — > записывает вывод в файл и может перезаписать его; >> дописывает в конец. В готовых примерах не меняй их местами.
- `Ctrl+C и q` — Ctrl+C обычно прерывает работающую программу. Из просмотрщика less или некоторых длинных справок выходят буквой q. В nano используй его собственные сочетания.
- `Кавычки` — Объединяют текст с пробелами в один аргумент. Обычные прямые кавычки из кода подходят; типографские «ёлочки» вместо них вводить не надо.

### Ответы и ошибки

- **command not found** — Команда не найдена. Проверь написание, свой терминал (Windows или Linux) и установку нужного пакета.
- **Permission denied** — Недостаточно прав для конкретного действия. Проверь пользователя и путь; не выдавай всем 777.
- **No such file or directory** — Файл или папка не найдены. Проверь путь, регистр букв и выполнены ли предыдущие шаги.
- **Connection refused** — На указанном адресе/порту нет принимающего приложения или соединение отклонено. Проверь службу и слушающий порт.
- **Connection timed out** — Ответ не пришёл вовремя. Возможны маршрут, фильтрация или недоступный узел; один этот текст не доказывает причину.
- **Could not resolve host** — Не удалось получить адрес по имени. Начни с DNS и написания имени.
- **HTTP 200 / 403 / 404 / 502** — 200 — успешный HTTP-ответ; 403 — доступ запрещён; 404 — ресурс не найден; 502 — прокси не получил подходящий ответ от приложения.
- **active / inactive / failed** — active — unit активен; для службы обычно работает. inactive — сейчас не активен (для завершившегося oneshot бывает нормально). failed — запуск или работа завершились ошибкой.

## 1. Из чего состоит сервер

**Уровень:** Основа

Сервер — компьютер, который выполняет задачу для других. Сначала узнаем, кто на нём работает, как он называется и какой у него адрес.

**Результат:** Ты узнаёшь имя своей ВМ, версию Ubuntu и её IP-адрес.

**Для практики сначала:** предыдущие блоки не нужны.

**Цель:** Понимать, что именно ты добавляешь и какой результат должен получить.

**Параллель с Windows:** В Windows Server есть роли и службы. В Linux ту же задачу обычно собирают из пакета, файла настроек, службы и правил доступа.

Представь мастерскую. Железо — помещение; ядро — диспетчер оборудования; дистрибутив — готовый набор инструментов. Установленная программа ещё не обязательно работает: за постоянную работу обычно отвечает служба.

Новая роль сервера собирается по одной схеме: установить пакет → изменить конфигурацию → проверить её → включить службу → разрешить нужный доступ → проверить с другого компьютера. Например, Nginx превращает сервер в площадку для сайтов.

Для упражнений удобна отдельная виртуальная машина: 2 виртуальных процессора, 2–4 ГБ памяти, 20–30 ГБ диска. Это ориентир для простых уроков. Выбирай Ubuntu Server 24.04 LTS из официального источника и не отмечай ненужные роли.

В установщике задают язык и клавиатуру, сеть, имя сервера, пользователя и диск. Выбор диска может стереть данные: в учебной машине выбирай именно её виртуальный диск. Создай обычного пользователя с sudo и установи OpenSSH, если нужен вход с Windows. После установки вынь ISO-образ из виртуального привода.

Запиши имя виртуальной машины, дистрибутив, IP, способ доступа и назначение. Пароли и закрытые ключи в такую заметку не добавляют. Перед важным опытом полезен снимок ВМ, а для данных нужна отдельная резервная копия.

### Где это находится

- /etc — Настройки системы и установленных служб
- /var — Изменяющиеся данные: журналы, очереди, базы
- /home — Личные каталоги пользователей
- /srv — Удобное место для данных своих серверных задач

### Команды и настройки

#### 1. Узнать, куда вошёл

**Формат:** Команда Linux · терминал сервера.

**Где:** На Linux после установки. **Тип:** Только чтение.

Показывает пользователя, имя компьютера, дистрибутив и адреса интерфейсов.

```bash
whoami
hostnamectl
cat /etc/os-release
ip -br address
```

**Проверка:** Сопоставь имя, версию и IP с карточкой своей ВМ.

#### 2. Посмотреть общую картину

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает время работы, память, диски и занятое место.

```bash
uptime
free -h
lsblk -f
df -h
```

**Проверка:** Не путай размер диска из lsblk со свободным местом файловой системы из df.

### Наглядный обмен

**Что происходит при добавлении роли**

1. Администратор → Пакет: Сначала получаем программу из доверенного репозитория.
2. Администратор → Настройки: Пишем, какие файлы отдавать, где слушать и кому разрешать доступ.
3. Настройки → Служба: После проверки служба перечитывает настройки и начинает выполнять задачу.
4. Служба → Администратор: Проверяем результат локально и с компьютера пользователя.

**Путь к работающему сайту**

1. Браузер → Сеть: Браузер узнаёт адрес и пытается установить соединение.
2. Сеть → Firewall: Сеть должна довести соединение до нужного порта сервера.
3. Firewall → Веб-служба: Firewall пропускает разрешённое соединение к работающей программе.
4. Веб-служба → Браузер: Открытый порт сам по себе ещё не подтверждает правильную страницу.

### Микро-проверка

Пакет Nginx уже установлен. Сайт точно работает?

1. Да, установки достаточно
2. Нужно проверить службу, настройки и доступ
3. Нужно только перезагрузить Windows

**Разбор:** Нужно проверить службу, настройки и доступ. Установка даёт программу. Работу сайта подтверждает ответ нужного приложения, в том числе с другого компьютера.

## 2. Терминал и папки

**Уровень:** Основа

Терминал — способ сказать компьютеру, что сделать. Команды здесь заменяют отдельные действия мышью в Проводнике.

**Результат:** Ты создал личный notes.txt, сохранил его и увидел свой текст через cat.

**Для практики сначала:** Из чего состоит сервер.

**Цель:** Ориентироваться в файловой системе и спокойно менять учебный файл.

**Параллель с Windows:** Проводник соответствует работе с папками, а PowerShell ближе всего к оболочке Bash. Дисков C: и D: здесь нет: есть общее дерево от /.

Терминал — окно общения с командной оболочкой. Оболочка читает команду и запускает программу. В приглашении student@linux-lab:~$ часть до $ сообщает пользователя, сервер и папку. Сам знак $ переписывать не надо.

Вводишь одну строку → нажимаешь Enter → читаешь ответ. Если команда попросила пароль, символы не показываются: введи пароль и нажми Enter. При ошибке не переходи к следующей строке.

Путь / начинается с корня всей системы. Путь ~ означает домашнюю папку текущего пользователя. Точка — текущая папка, две точки — родительская. В Linux Report.txt и report.txt — разные имена.

ls показывает содержимое, cd меняет папку, pwd показывает текущий путь. Tab дополняет имя, стрелка вверх возвращает прошлую команду. Пробелы разделяют аргументы; путь с пробелами заключай в кавычки.

В Windows Terminal копирование и вставка обычно Ctrl+Shift+C и Ctrl+Shift+V; Ctrl+V зависит от настройки терминала. Ctrl+C в оболочке обычно прерывает выполняющуюся программу. В редакторе nano действуют его собственные сочетания: Ctrl+O, Enter — сохранить; Ctrl+X — выйти.

Для настроек удобно sudoedit: команда открывает копию файла в редакторе и затем сохраняет её с правами администратора. Можно выбрать nano через SUDO_EDITOR=nano. Перед изменением существующего файла сделай его отдельную копию с понятным именем.

### Где это находится

- /home/student — Пример домашней папки пользователя student
- /etc — Системные настройки: редактирование обычно требует sudo
- /tmp — Временные файлы; постоянные данные здесь не держат

### Команды и настройки

#### 1. Осмотреться

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Последовательно показывает путь, файлы, переход к настройкам и возвращение домой.

```bash
pwd
ls -lah
cd /etc
ls
cd ~
```

**Проверка:** После cd ~ команда pwd должна показать домашнюю папку твоего пользователя.

#### 2. Создать свой учебный файл

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Создаёт личную папку и открывает notes.txt. Напечатай, например: «Моя первая заметка». Сохрани Ctrl+O, Enter и выйди Ctrl+X.

```bash
mkdir -p ~/linux-study
nano ~/linux-study/notes.txt
```

**Проверка:** cat ~/linux-study/notes.txt должен показать именно «Моя первая заметка». Если nano не найден, установи его через apt, как описано в стартовой памятке.

**Возврат / ограничения:** Оставь папку как конспект либо удали только созданный учебный файл через rm ~/linux-study/notes.txt.

#### 3. Скопировать и сравнить

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Сначала делает копию, затем позволяет изменить текст и увидеть разницу.

```bash
cp -a ~/linux-study/notes.txt ~/linux-study/notes.before.txt
nano ~/linux-study/notes.txt
diff -u ~/linux-study/notes.before.txt ~/linux-study/notes.txt
```

**Проверка:** В diff строки с минусом — прежние, с плюсом — новые; код 1 означает найденные различия.

**Возврат / ограничения:** cp -a ~/linux-study/notes.before.txt ~/linux-study/notes.txt

**Уточнение:** Сначала нужен сохранённый notes.txt из предыдущей карточки. После копирования измени одну строку в notes.txt, сохрани файл и только затем запускай diff.

### Наглядный обмен

**Команда встречает файл**

1. Ты → Оболочка: Ты вводишь команду, например cat notes.txt.
2. Оболочка → Каталог: Относительный путь ищется внутри текущей папки.
3. Каталог → Файл: Система проверяет право читать этот файл.
4. Файл → Ты: Содержимое возвращается в терминал; сам cat файл не меняет.

### Микро-проверка

Что обычно сделает Ctrl+C в работающем терминале?

1. Скопирует весь экран
2. Отправит программе сигнал прерывания
3. Сохранит файл nano

**Разбор:** Отправит программе сигнал прерывания. Это команда прерывания. Для копирования в Windows Terminal обычно используют Ctrl+Shift+C или выделение с настроенным копированием.

## 3. Пользователи и sudo

**Уровень:** Основа

Сначала создаём человеку отдельную учётную запись. Затем решаем, какие папки он видит и нужно ли ему управление сервером.

**Результат:** Учебный пользователь anna существует, а его группы видны через id.

**Для практики сначала:** Терминал и папки.

**Цель:** Добавить отдельную учётную запись и выдать ровно нужные права.

**Параллель с Windows:** Обычный пользователь похож на учётную запись Windows, группа — на локальную группу. sudo позволяет выполнить конкретное действие с повышенными правами.

root — самый привилегированный пользователь. Для повседневной работы удобнее личная учётная запись и sudo для отдельных административных действий. Пароль sudo обычно относится к твоей учётной записи.

Пользователь имеет имя и числовой UID. Группы объединяют доступ: например, участники project могут вместе работать с папкой. Службам часто выделяют отдельные системные учётные записи без обычного входа.

В Ubuntu adduser создаёт обычного пользователя с домашней папкой и задаёт пароль. usermod -aG добавляет к дополнительной группе. Ключ -a важен: без него можно заменить прежний список групп.

Новые группы обычно появляются в новой сессии. Проверь id пользователя и отдельно войди под ним. Членство в группе sudo на Ubuntu — широкие права администратора; это не просто право читать файлы.

### Позже: дополнительные подробности

При увольнении сотрудника отключают пароль, ключи SSH и другие способы входа, отзывают sudo и разбирают существующие сессии. passwd -l блокирует пароль, но само по себе не отзывает ключи SSH.

### Где это находится

- /etc/passwd — Список учётных записей; здесь нет обычных паролей
- /etc/group — Локальные группы
- /etc/shadow — Защищённые сведения о паролях
- /etc/sudoers.d — Дополнительные правила sudo; редактируют через visudo

#### 1. Посмотреть свою учётную запись

**Возврат / ограничения:** sudo deluser anna sudo убирает членство в группе sudo. Другие правила sudo и уже выданные полномочия проверь отдельно.

**Уточнение:** Необязательное упражнение для отдельного администратора. Для дальнейшей общей папки anna не нужны права sudo: этот шаг можно пропустить.

## 4. Файлы и права доступа

**Уровень:** Основа

У файла есть хозяин и правила: кто читает, кто меняет, а кто вообще не имеет доступа.

**Результат:** Анна может создать файл в общей папке project; посторонним она закрыта.

**Для практики сначала:** Терминал и папки, Пользователи и sudo.

**Цель:** Разобрать rwx и сделать общую папку без разрешения 777.

**Параллель с Windows:** Похоже на права NTFS, но базовая модель Linux отдельно задаёт владельца, группу и остальных. При необходимости добавляют ACL.

У файла есть владелец, группа и права для трёх наборов людей: владелец / группа / остальные. r — чтение, w — запись, x — выполнение. Цифры складываются: r=4, w=2, x=1. Поэтому 6 — чтение и запись, а 7 — все три права.

У папки x означает «можно пройти внутрь», r — «можно увидеть список имён». Для создания и удаления файлов в этой папке обычно нужны w и x. Поэтому права самой папки тоже важны, даже если у файла стоит разрешение на чтение.

chmod 640 файл даёт владельцу чтение и запись, группе чтение, остальным ничего. chmod 750 папка позволяет владельцу всё, группе смотреть и проходить, остальным ничего. Один набор прав для всех файлов и папок обычно не подходит.

В общей папке удобно автоматически давать новым файлам группу project. Для этого на папке включают setgid: в числе 2770 первая 2 включает этот флажок, а 770 — обычные права владельца, группы и остальных. Групповая запись дополнительно зависит от umask и программы, создавшей файл.

Не лечи Permission denied командой chmod -R 777. Сначала выясни пользователя службы, владельца файла и права всех родительских папок. Для дополнительных точечных правил существует ACL; его можно изучить после базовой модели.

### Позже: дополнительные подробности

Если базовых прав не хватает, существуют дополнительные ACL и специальный sticky bit. Их изучают после обычных rwx; для упражнения с project они не обязательны.

### Где это находится

- /srv/project — Пример общей папки
- /home/anna — Личная папка anna, не общая директория сайта
- /etc/group — Членство в группах для общего доступа

### Команды и настройки

#### 1. Проверить путь и владельцев

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает разрешения папки и каждого компонента пути.

```bash
ls -ld /srv /srv/project
namei -l /srv/project
```

**Проверка:** Если /srv/project ещё не создан, ошибка его отсутствия ожидаема.

#### 2. Создать общую папку

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Даёт доступ участникам project; 2 впереди включает наследование группы для новых объектов.

```bash
sudo addgroup project
sudo usermod -aG project anna
sudo mkdir -p /srv/project
sudo chown root:project /srv/project
sudo chmod 2770 /srv/project
```

**Проверка:** После нового входа anna: id; затем touch /srv/project/anna-test.txt и ls -l /srv/project.

**Возврат / ограничения:** Убрать anna из project: sudo deluser anna project. Старое членство действует в уже открытых сессиях; переподключись.

**Уточнение:** Учебные группа project и папка должны быть новыми. Не меняй владельцев существующих рабочих каталогов по этому примеру.

#### 3. Задать права отдельному файлу

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Делает личный учебный файл читаемым и изменяемым владельцем, читаемым группой.

```bash
chmod 640 ~/linux-study/notes.txt
ls -l ~/linux-study/notes.txt
```

**Проверка:** Начало строки должно быть -rw-r-----.

**Возврат / ограничения:** Верни ранее записанные права только этого файла, если они нужны.

### Наглядный обмен

**Три набора прав**

1. Владелец → Файл 640: Владелец читает и записывает: 4+2=6.
2. Группа → Файл 640: Группа только читает: 4.
3. Остальные → Файл 640: Остальным доступа нет: 0.
4. Владелец → Файл 640: Для обычной проверки прав сначала берётся подходящий класс владельца, затем группы или остальных; ACL и привилегии могут менять результат.

1. Он запускается как программа
2. Можно проходить по пути и обращаться к именам
3. Любой может менять его содержимое

**Разбор:** Можно проходить по пути и обращаться к именам. У каталогов x — право прохода. Оно нужно на каждом родительском каталоге пути.

## 5. Установка программ и обновления

**Уровень:** Основа

Новые возможности добавляют установкой программ из проверенного каталога. Обновить список программ и установить обновления — два разных действия.

**Результат:** Списки пакетов обновлены без ошибок, выбранная программа установлена.

**Для практики сначала:** Терминал и папки.

**Цель:** Установить пакет, понять зависимости и отличить update от upgrade.

**Параллель с Windows:** apt похож на управляемую установку через пакетный менеджер. Репозитории — настроенные каталоги доверенных пакетов.

Репозиторий хранит пакеты и метаданные о них. apt выбирает подходящие версии и зависимости — другие нужные пакеты. На Ubuntu не нужно искать случайный setup.exe для каждой программы.

Слово update здесь означает «узнать, что есть в каталоге», а upgrade — «поставить новые версии». После apt update установленные программы ещё те же.

apt update обновляет список доступных версий. apt upgrade устанавливает обновления уже установленных пакетов. Это разные действия. Перед обновлением рабочего сервера изучают список изменений и план восстановления.

Установка серверного пакета может автоматически запустить службу. Поэтому предварительно учитывают сеть и firewall. Удаление пакета не равно безопасному удалению всех его данных.

Проверь /var/run/reboot-required: Ubuntu может запросить перезагрузку после обновления. Это не означает, что сервер можно перезагрузить прямо сейчас. Нужны окно обслуживания, проверенная копия и понимание, какие пользователи зависят от служб.

### Позже: дополнительные подробности

Для обычного администрирования apt удобен. Для автоматизации часто используют apt-get с осознанными параметрами. Не добавляй -y и сторонние репозитории, пока не понимаешь итоговый список действий.

### Где это находится

- /etc/apt/sources.list.d — Дополнительные источники пакетов; в новых Ubuntu часто файлы .sources
- /var/log/apt/history.log — История операций apt
- /var/run/reboot-required — Признак запрошенной перезагрузки, если файл существует

### Команды и настройки

#### 1. Обновить списки и увидеть предложения

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Обновляет локальные списки.

Получает актуальные сведения из уже настроенных репозиториев; вторая команда показывает доступные обновления.

```bash
sudo apt update
apt list --upgradable
```

**Проверка:** apt update должен завершиться без ошибок источников и подписи.

**Возврат / ограничения:** Системные пакеты пока не обновлялись; повторно обнови списки после исправления источников.

#### 2. Установить полезные инструменты

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Добавляет HTTP-клиент, редактор, просмотр процессов и команды диагностики DNS.

```bash

```

**Проверка:** curl --version; nano --version; command -v htop; command -v dig.

**Возврат / ограничения:** Сначала посмотри sudo apt remove --simulate htop; удаляй только пакеты, добавленные именно для упражнения.

#### 3. Предварительно увидеть обновление

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** План без установки.

Показывает план изменений пакетов, не устанавливая их.

```bash
sudo apt upgrade --simulate
```

**Проверка:** Изучи удаления, новые зависимости и изменения служб. Реальное обновление: sudo apt upgrade в согласованное окно.

#### 4. Проверить запрос перезагрузки

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Читает признак Ubuntu о необходимости перезагрузки.

```bash

```

**Проверка:** Отсутствие этого файла не гарантирует, что все приложения уже используют новые библиотеки.

### Наглядный обмен

**Как пакет попадает на сервер**

1. apt → Репозиторий: Загружается каталог версий; сами установленные программы ещё не обновляются.
2. apt → Пакеты: Выбираются пакет и его зависимости, проверяется доверенная цепочка метаданных.
3. Пакеты → Служба: Пакет размещает файлы; серверная служба может запуститься автоматически.
4. Служба → apt: Проверяешь версию, состояние службы и нужную функцию.

3. Перезагружает сервер

**Разбор:** Обновляет список доступных пакетов. Для установки обновлений служит отдельное действие upgrade.

## 6. Вход с Windows по SSH

**Уровень:** Основа

SSH открывает терминал сервера с твоего Windows-компьютера. Ключ позволяет подтвердить, что входишь именно ты.

**Результат:** Из нового окна Windows выполнен вход на свою ВМ по ключу.

**Для практики сначала:** Терминал и папки, Установка программ и обновления.

**Цель:** Подключаться с ключом и проверять настройки до их применения.

**Параллель с Windows:** По назначению это близко к удалённому управлению через PowerShell. Ты получаешь терминал Linux, а не рабочий стол через RDP.

SSH шифрует соединение между клиентом и сервером. В Windows есть клиент ssh; на Linux нужна серверная часть OpenSSH. Стандартный порт — TCP 22. Первый вопрос об отпечатке ключа — проверка личности сервера, а не формальность.

У пары SSH-ключей есть открытая и закрытая части. Открытую строку добавляют на сервер в authorized_keys. Закрытый файл остаётся у тебя, обычно защищён кодовой фразой. Никому не отправляй закрытую часть.

Сначала подключись прежним способом, добавь открытый ключ и открой второе окно Windows с входом по этому ключу. Старое окно оставь открытым. Дополнительно проверь, что доступна консоль ВМ или хостинга.

В простом маршруте достаточно: установить OpenSSH → войти с Windows → добавить открытый ключ → проверить вход из нового окна. Ужесточение способов входа — отдельный следующий шаг в карточках с пометкой «Позже».

### Позже: дополнительные подробности

Файлы sshd_config.d помогают отделить свои настройки, но у OpenSSH для большинства директив действует первое найденное значение. Имя файла само по себе не гарантирует приоритет. sshd -T показывает эффективную конфигурацию; при правилах Match используй также -C с реальными параметрами подключения.

Отключать пароль имеет смысл только после успешного нового входа по ключу у всех нужных администраторов. Не меняй порт ради первого упражнения: в Ubuntu встречается запуск через ssh.socket, а изменение адреса/порта требует отдельного разбора socket activation.

**Перед изменением:** Доступ к SSH меняют при открытой рабочей сессии и доступной консоли. Проверки sshd -t и нового входа обязательны; окно с уже открытой сессией само по себе не доказывает, что новые входы работают.

### Где это находится

- ~/.ssh/authorized_keys — На сервере: разрешённые открытые ключи этого пользователя
- ~/.ssh/id_ed25519 — На клиенте: закрытый ключ; не передавать
- /etc/ssh/sshd_config.d — Дополнительные настройки SSH-сервера
- /etc/ssh/sshd_config — Главный конфигурационный файл

### Команды и настройки

#### 1. Установить сервер SSH

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Устанавливает OpenSSH и показывает варианты запуска и слушающие порты.

```bash
sudo apt install openssh-server
systemctl status ssh.service ssh.socket --no-pager
sudo ss -lntp
```

**Проверка:** Нужен доступный TCP 22. Неактивная ssh.service при активной ssh.socket сама по себе не доказывает поломку.

**Возврат / ограничения:** Сначала подготовь консоль ВМ; остановка или удаление OpenSSH прервёт возможность новых входов.

**Уточнение:** Проверь также firewall самой ВМ и правила хостинга. Для входа с Windows оставь консоль ВМ открытой и запиши её фактический IP.

#### 2. Посмотреть отпечаток через консоль ВМ

**Формат:** Команда Linux · терминал сервера.

**Где:** В доверенной консоли учебной Linux-ВМ. **Тип:** Только чтение.

Показывает отпечаток открытого ключа сервера, если такой host key существует. Открой эту команду через доверенную консоль ВМ, а не через ещё не проверенное SSH-соединение.

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

**Проверка:** При первом входе с Windows сравни значение SHA256 и тип ED25519 с тем, что показала консоль. Если клиент показывает другой тип ключа, нужно сверить соответствующий открытый host key.

**Уточнение:** Это открытый ключ самого сервера. Он отличается от твоего пользовательского ключа id_ed25519.

#### 3. Создать ключ и подключиться

**Формат:** Команда Windows · PowerShell.

**Где:** В PowerShell на Windows. **Тип:** Меняет настройки.

На Windows создаёт пару ключей, показывает открытый ключ и запускает клиент.

**Подстановка:** Замени 192.0.2.10 на реальный IP своей ВМ; student — на имя своего пользователя. Вводить нужно в PowerShell на Windows.

```powershell
ssh-keygen -t ed25519
Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
ssh student@192.0.2.10
```

**Проверка:** Подставь настоящий адрес ВМ. Отпечаток сервера сверь через доверенную консоль. Если ключ уже существует, не перезаписывай его.

**Уточнение:** 192.0.2.10 — документационный адрес, он не является адресом твоего сервера.

#### 4. Добавить открытый ключ на сервер

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Открой файл под тем пользователем, которому разрешаешь вход, и добавь ОТКРЫТУЮ строку отдельной строкой.

```bash
install -d -m 700 ~/.ssh
nano ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

**Проверка:** Из нового окна Windows: ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no student@АДРЕС_ВМ. Должен пройти вход по ключу.

**Возврат / ограничения:** Удали только добавленную строку из authorized_keys, сохранив другие ключи.

**Уточнение:** Кодовая фраза ключа запрашивается на клиенте и отличается от пароля пользователя Linux.

#### 5. Позже: отдельный файл ограничений SSH

**Формат:** Содержимое файла · Дополнительный шаг.

**Где:** В /etc/ssh/sshd_config.d/00-lab-hardening.conf. **Тип:** Образец конфигурации.

Это содержимое нового файла настроек. Оно запрещает прямой вход root и способы входа по паролю. Создавай файл только после успешного нового входа по ключу у всех нужных администраторов и проверки запасной консоли.

**Это текст файла `/etc/ssh/sshd_config.d/00-lab-hardening.conf`. Его не выполняют напрямую в терминале.**

Открой файл на Linux:

```bash
SUDO_EDITOR=nano sudoedit /etc/ssh/sshd_config.d/00-lab-hardening.conf
```

Вставь в новый учебный файл. Если файл существует, сначала сохрани и разбери прежнее содержимое.

Сохранение в nano: Ctrl+O (латинская O) → Enter → Ctrl+X. Затем выполни проверку из карточки.

```text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
```

**Проверка:** Следующая карточка проверяет sshd -t и эффективные параметры sshd -T. При MFA нужны другие настройки: этот учебный фрагмент туда не переносят.

**Возврат / ограничения:** Убери только свой новый файл или восстанови его сохранённую версию через открытую консоль, проверь синтаксис и способ применения.

**Уточнение:** Для базового упражнения со входом по ключу эту карточку можно пропустить.

#### 6. Проверить настройку перед применением

**Формат:** Команда Linux · терминал сервера · Дополнительный шаг.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Проверяет синтаксис и эффективные параметры; reload применяет изменения к уже работающей службе.

```bash
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | grep -E '^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '
sudo systemctl reload ssh.service
```

**Проверка:** После успешного reload открой новое соединение и повтори проверку sudo. Если ssh.service не запущена и работает только socket, не запускай команды вслепую: сначала подтверди способ запуска через консоль.

**Возврат / ограничения:** Верни изменённый файл из своей копии, снова выполни sshd -t и reload, затем проверь новый вход.

**Уточнение:** Только после проверки ключей и подготовки отдельного файла. Первое найденное значение SSH обычно побеждает последующие, поэтому нужен sshd -T. Для Match добавляют -C с фактическими параметрами подключения. Адрес и порт SSH в упражнении не меняем.

### Наглядный обмен

**Как ключ разрешает вход**

1. Windows → SSH-сервер: Клиент проверяет ключ сервера по известному отпечатку.
2. SSH-сервер → Открытый ключ: Сервер ищет открытый ключ нужного пользователя.
3. Windows → SSH-сервер: Клиент доказывает владение закрытым ключом, не передавая сам ключ.
4. SSH-сервер → Linux-пользователь: После успешных проверок создаётся сессия с правами конкретного пользователя.

**Как менять доступ**

1. Старое окно → Ключ: Сохраняешь открытый ключ, не закрывая рабочую сессию.
2. Ключ → Новое окно: Проверяешь новый вход именно по ключу.
3. Старое окно → Настройки SSH: Делаешь копию конфигурации, правку и sshd -t; смотришь sshd -T.
4. Настройки SSH → Новое окно: Применяешь настройки и снова входишь новым соединением. Старое закрываешь только после проверки.

## 7. Службы и автозапуск

**Уровень:** Основа

Установленная программа не обязательно запущена. Служба позволяет ей работать без открытого окна терминала.

**Результат:** Ты различаешь «работает сейчас» и «запустится после включения сервера».

**Для практики сначала:** Установка программ и обновления.

**Цель:** Отличать состояние сейчас от запуска после перезагрузки.

**Параллель с Windows:** systemctl — примерно консоль управления службами Windows. journalctl помогает читать их журналы.

systemd управляет многими частями современной Ubuntu: службами, запуском по времени и зависимостями. Его единица конфигурации — unit, например nginx.service.

start запускает службу сейчас; stop останавливает; restart останавливает и запускает заново. reload просит перечитать настройки и работает только у служб, которые его поддерживают.

Быстрая расшифровка: active (running) — служба работает; failed — была ошибка; enabled — включён автозапуск. inactive может быть нормальным состоянием уже завершившегося разового задания.

enable настраивает запуск при загрузке, но обычно не запускает службу немедленно. enable --now делает оба действия. active говорит о состоянии сейчас; enabled — об участии в запуске. Службы static и socket-activated могут нормально работать без enabled.

После изменения файла самой программы сначала проверь синтаксис её командой. После изменения unit-файла systemd нужен daemon-reload. Он перечитывает описание unit и сам по себе не перезапускает приложение.

Если служба упала, сначала читают причину. Бесконечные restart маскируют проблему и могут испортить ситуацию. Проверяй конфигурацию, путь к файлам, права, свободное место и занятый порт.

Примеры ниже используют Nginx. Если ты ещё не проходил блок сайта, пока прочитай их как объяснение и вернись после установки Nginx. Сообщение Unit nginx.service could not be found в этом случае означает, что пакет ещё не добавлен.

### Где это находится

- /etc/systemd/system — Свои unit-файлы и переопределения
- /usr/lib/systemd/system — Поставляемые пакетами unit-файлы; /lib может вести сюда
- /etc/systemd/system/ИМЯ.service.d — Переопределения через systemctl edit

### Команды и настройки

#### 1. Посмотреть службу

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает текущее состояние, автозапуск и полное описание unit с дополнениями.

```bash
systemctl status nginx --no-pager
systemctl is-active nginx
systemctl is-enabled nginx
systemctl cat nginx
```

**Проверка:** Если Nginx ещё не установлен, unit не найден — это ожидаемо. Вернись после урока о сайте.

#### 2. Включить автозапуск и запустить

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Подключает Nginx к автозапуску и запускает сейчас.

```bash
sudo systemctl enable --now nginx
```

**Проверка:** systemctl is-active nginx; systemctl is-enabled nginx; curl -I http://127.0.0.1.

**Возврат / ограничения:** Если служба добавлена только для урока: sudo systemctl disable --now nginx. Запиши прежнее состояние до изменения.

**Уточнение:** Выполняй после установки nginx из блока «Добавляем сайт: Nginx». До этого карточку можно прочитать без выполнения.

#### 3. Увидеть причину сбоя

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Читает последние сообщения Nginx текущей загрузки и список проблемных unit.

```bash
sudo journalctl -u nginx -b -n 60 --no-pager
systemctl --failed
```

**Проверка:** Ищи первую осмысленную ошибку перед выходом процесса, а не только слово failed.

### Наглядный обмен

**Сейчас и после загрузки**

1. Администратор → start: start отвечает только за текущее состояние.
2. start → Служба: Программа выполняется. Она не обязательно включена на следующую загрузку.
3. Администратор → enable: enable связывает unit с нужной точкой загрузки.
4. enable → Служба: enabled не гарантирует успешный запуск: ошибка конфигурации всё равно может остановить службу.

### Микро-проверка

1. Да
2. Нет, для этого нужен start или enable --now
3. Да, если есть интернет

**Разбор:** Нет, для этого нужен start или enable --now. Автозапуск и текущее состояние — разные вещи. Исключения вроде socket activation разбирают отдельно.

## 8. Сеть: адрес, маршрут и DNS

**Уровень:** Практика

Адрес отвечает «где сервер», маршрут — «куда отправлять», DNS — «какой адрес у имени». Проверяем их по отдельности.

**Результат:** Ты нашёл интерфейс, IP, маршрут и DNS своей ВМ. Менять их ради урока необязательно.

**Для практики сначала:** Из чего состоит сервер, Вход с Windows по SSH.

**Цель:** Проверить сеть по слоям и понять пример статического IP в Netplan.

**Параллель с Windows:** ip address похоже на просмотр IP в Windows, ip route — на route print, DNS-клиент показывает resolvectl.

Для первого знакомства просто посмотри текущую сеть. Статический IP не нужен ради прохождения урока: адрес может выдавать DHCP. Менять адрес следует только при известной задаче и подготовленной консоли.

У интерфейса есть имя, например enp1s0, и IP-адрес с префиксом. Шлюз передаёт пакеты в другие сети. DNS помогает найти адрес по имени. Это три разные настройки.

Начни с ip -br address, ip route и resolvectl status. Запрос по IP может работать при сломанном DNS; работающий DNS ещё не доказывает доступность TCP-порта и самого приложения. Отсутствие ответа ping тоже не всегда означает недоступность: ICMP могут фильтровать.

В Ubuntu Server сеть часто описана в Netplan: YAML-файлы в /etc/netplan. Файлы объединяются по правилам Netplan. Нельзя бездумно добавить второй конфликтующий файл поверх существующей конфигурации.

Для постоянного адреса проще начать с резервации DHCP на роутере или в панели хостинга. Если меняешь адрес внутри Linux, сначала узнай имя интерфейса, подсеть, свободный адрес, шлюз и подходящие DNS. Учебные адреса 192.0.2.0/24 предназначены для документации.

netplan generate проверяет и генерирует конфигурацию без обычного применения. netplan try предлагает временное применение с подтверждением и попыткой отката по тайм-ауту. Откат не заменяет доступную консоль; после отказа нужно проверить фактическое состояние.

### Позже: дополнительные подробности

Облачный образ может управляться cloud-init, NetworkManager или панелью провайдера. Сначала выясни владельца конфигурации: ручной файл способен конфликтовать с его генератором. Не отключай cloud-init по случайному примеру.

**Перед изменением:** Статическую сеть меняют только после записи исходной конфигурации и проверки доступа к консоли ВМ/хостинга. Адреса в образце не подходят для копирования в настоящую сеть.

### Где это находится

- /etc/netplan/*.yaml — Описание постоянной сети в выбранной Ubuntu
- /etc/hosts — Локальные соответствия имён и адресов; не полноценная замена DNS
- /etc/resolv.conf — Часто управляемая ссылка; не редактируют вслепую
- /etc/hostname — Постоянное имя узла

### Команды и настройки

#### 1. Собрать исходные данные

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает интерфейсы, маршруты, DNS и объединённую Netplan-конфигурацию.

```bash
ip -br address
ip route
resolvectl status
ls -l /etc/netplan
sudo netplan get
```

**Проверка:** Запиши фактические имя интерфейса, адрес, default route и DNS. Вывод может содержать внутренние сведения сети: не публикуй его целиком.

#### 2. Пример содержимого YAML

**Формат:** Содержимое файла · Дополнительный шаг.

**Где:** В выбранном существующем YAML-файле /etc/netplan. **Тип:** Образец конфигурации.

Объясняет структуру файла: интерфейс, адрес, маршрут и DNS. Пробелы важны; табуляции не используют.

**Это текст файла `/etc/netplan/твой-действующий-файл.yaml`. Его не выполняют напрямую в терминале.**

Сначала найди действующий файл через ls -l /etc/netplan и netplan get. Путь выше — образец; сохрани остальные нужные сетевые настройки.

Измени только разобранные поля своего файла.

Сохранение в nano: Ctrl+O (латинская O) → Enter → Ctrl+X. Затем выполни проверку из карточки.

```text
network:
  version: 2
  renderer: networkd
  ethernets:
    enp1s0:
      dhcp4: false
      addresses: [192.0.2.10/24]
      routes:
        - to: default
          via: 192.0.2.1
      nameservers:
        addresses: [192.0.2.53]
```

**Проверка:** Это образец СОДЕРЖИМОГО файла, не команда. Все адреса и имя интерфейса нужно заменить фактическими.

**Возврат / ограничения:** Сохрани исходный файл и его права до правки; в случае потери сети восстанови через консоль.

#### 3. Проверить и пробно применить

**Формат:** Команда Linux · терминал сервера · Дополнительный шаг.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Сначала проверяет структуру, затем предлагает временно применить сеть с подтверждением.

```bash
sudo netplan generate
sudo netplan try --timeout 120
```

**Проверка:** Через новую сессию проверь SSH, ip route и resolvectl query example.com. Подтверждай только рабочую конфигурацию.

**Возврат / ограничения:** Если сеть потеряна, открой консоль, восстанови сохранённую конфигурацию и проверь применение. Тайм-аут — дополнительная защита, не гарантия.

**Уточнение:** Только в учебной ВМ с доступной консолью. Права YAML обычно 600. Сохраняй текущий renderer и настройки IPv6, если не разбираешь их отдельно.

#### 4. Отделить DNS от HTTP

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Чтение и сетевые запросы.

Первая команда проверяет разрешение имени, вторая — подключение и HTTP поверх TLS.

```bash
resolvectl query example.com
curl -I --connect-timeout 5 https://example.com
```

**Проверка:** Сравни этапы ошибки curl: имя, соединение, сертификат, HTTP-код.

### Наглядный обмен

**Три разных решения**

1. Сервер → DNS: DNS сообщает, какой адрес соответствует имени сайта.
2. DNS → Сервер: Получение IP ещё не значит, что путь до него доступен.
3. Сервер → Шлюз: Таблица маршрутов выбирает интерфейс и следующий узел.
4. Шлюз → Сайт: Затем проверяются TCP, TLS и само приложение.

**Как менять постоянную сеть**

1. Текущая сеть → Копия YAML: Сначала фиксируешь исходный файл и рабочий способ доступа.
2. Копия YAML → netplan try: Проверяешь generate и временно применяешь изменения.
3. netplan try → Новая сессия: Новое подключение подтверждает доступность по новой конфигурации.
4. Новая сессия → Текущая сеть: Подтверждаешь рабочую сеть или восстанавливаешь исходную через консоль.

### Микро-проверка

IP-адрес сайта известен, но имя не разрешается. Что проверить первым?

1. DNS-клиент и его серверы
2. Права chmod на сайт
3. Группу sudo

**Разбор:** DNS-клиент и его серверы. Нахождение адреса по имени — отдельная задача DNS. После её исправления всё равно проверяют соединение и приложение.

## 9. Firewall и открытые порты

**Уровень:** Практика

Firewall похож на список разрешённых входов. Он пропускает соединение, но не запускает программу за дверью.

**Результат:** Понятно, какой порт разрешён, кто его слушает и получает ли ответ клиент.

**Для практики сначала:** Сеть: адрес, маршрут и DNS, Вход с Windows по SSH.

**Цель:** Разрешать нужную службу и различать firewall, слушающий порт и внешнюю сеть.

**Параллель с Windows:** UFW — удобная оболочка управления сетевыми правилами Linux, близкая по назначению к Windows Firewall.

Порт — номер точки входа в программу, например TCP 22 у SSH и TCP 443 у HTTPS. Слушающий сокет создаёт программа. Firewall решает, какие соединения пропустить; он не запускает программу.

Правило отвечает «можно ли пройти», а служба — «есть ли кто-то за дверью». Проверки делятся так: ss — кто слушает; ufw status — что разрешено; запрос с Windows — доходит ли соединение и что отвечает.

В Ubuntu можно использовать UFW. Перед включением сначала разреши реальный порт SSH от реального административного адреса или VPN-подсети. Адрес источника должен быть тем, который виден серверу, с учётом NAT.

Работать могут сразу несколько уровней: firewall Linux, правила облака, роутер/NAT и корпоративная сеть. Открыть UFW недостаточно, если соединение не доходит до сервера.

Если программа слушает только 127.0.0.1, она доступна только локально. Слушание 0.0.0.0 означает все IPv4-интерфейсы; IPv6 проверяют отдельно. Не нужно публиковать базу данных ради локального веб-приложения.

Docker и некоторые системы контейнеров сами добавляют правила перенаправления. Обычная оценка UFW не всегда описывает доступность опубликованных портов контейнера. Для учебного контейнера привязывай порт к 127.0.0.1.

**Перед изменением:** Порядок включения UFW показан для новой учебной машины. Не применяй его к рабочему серверу, не выяснив текущие правила, порт SSH и фактический адрес источника.

### Где это находится

- /etc/ufw — Постоянные настройки UFW
- sudo ufw status verbose — Удобный просмотр правил
- sudo ss -lntup — Фактически слушающие TCP/UDP-сокеты

### Команды и настройки

#### 1. Посмотреть исходное состояние

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Читает правила и реально слушающие программы.

```bash
sudo ufw status verbose
sudo ss -lntup
```

**Проверка:** Сравни нужный порт, протокол и адрес привязки программы.

#### 2. Учебный порядок включения

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Сперва разрешает SSH от администратора, затем задаёт политики и включает фильтрацию.

**Подстановка:** Сначала подставь адреса и имя интерфейса своей ВМ. Значения 192.0.2.* относятся к документационным примерам.

```bash
sudo ufw allow from 192.0.2.50 to any port 22 proto tcp
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw enable
```

**Проверка:** До выполнения замени 192.0.2.50 на свой фактический источник, 22 — на реальный SSH-порт. После — новая SSH-сессия и ufw status verbose.

**Возврат / ограничения:** Через открытую консоль восстанови прежние правила. Если UFW до урока был выключен, аварийно вернуться можно sudo ufw disable.

**Уточнение:** Это порядок для НОВОЙ учебной ВМ. На сервере с готовыми правилами сначала разбирают их и зависимости. Команды могут отрезать сеть.

#### 3. Разрешить веб-сайт

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Открывает входящий HTTP и HTTPS. Это не устанавливает веб-сервер и сертификат.

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status numbered
```

**Проверка:** Локально curl, затем запрос с другого компьютера. IPv6 и внешние правила оцени отдельно.

**Возврат / ограничения:** sudo ufw delete allow 80/tcp; sudo ufw delete allow 443/tcp — только если именно эти правила добавлены для урока.

#### 4. Проверить с Windows

**Формат:** Команда Windows · PowerShell.

**Где:** В PowerShell на Windows. **Тип:** Сетевые проверки.

Проверяет доступность TCP-порта с клиентского компьютера.

**Подстановка:** Замени 192.0.2.10 на реальный IP своей ВМ; student — на имя своего пользователя. Вводить нужно в PowerShell на Windows.

```powershell
Test-NetConnection 192.0.2.10 -Port 22
Test-NetConnection 192.0.2.10 -Port 80
```

**Проверка:** Замени документационный IP на реальный. TcpTestSucceeded не доказывает правильность авторизации SSH или содержимого сайта.

### Наглядный обмен

**Три двери на пути**

1. Клиент → Сеть хостинга: Пакет должен попасть на правильный IP и пройти правила внешней сети.
2. Сеть хостинга → UFW: Локальное правило сопоставляет источник, протокол и порт.
3. UFW → Программа: На нужном адресе и порту должна работать программа.
4. Программа → Клиент: Успех соединения проверяют отдельно от содержимого и прав в приложении.

### Микро-проверка

UFW разрешает TCP 80, но никто не слушает порт 80. Сайт заработает?

1. Да, firewall запустит сайт
2. Нет, нужно запустить и настроить программу
3. Да, после ping

**Разбор:** Нет, нужно запустить и настроить программу. Firewall разрешает соединения, а слушающий порт создаёт работающая программа.

## 10. Диски и постоянное подключение

**Уровень:** Практика

Дополнительный диск подключают к папке. Сам диск, его формат и эта папка — разные вещи.

**Результат:** Ты определил системный диск и проверил свободное место и число свободных inode.

**Для практики сначала:** Терминал и папки.

**Цель:** Понимать mount и fstab, проверять заполнение и не форматировать не тот диск.

**Параллель с Windows:** Вместо буквы D: дополнительный диск обычно подключают к папке, например /srv/data.

Сам диск, раздел на нём, файловая система и папка подключения — разные сущности. lsblk показывает дерево устройств. df показывает место уже смонтированных файловых систем.

Монтирование делает содержимое файловой системы доступным по папке. Например, данные отдельного диска можно видеть через /srv/data. Прежние файлы этой папки при монтировании скрываются, но не исчезают.

При включении серверу надо снова подключить диск. Для этого используют /etc/fstab. В записи удобно указывать UUID — идентификатор файловой системы: имя вроде /dev/sdb может измениться. Сначала учимся читать готовые подключения; править fstab для этого необязательно.

На новом пустом диске создают таблицу разделов, раздел и файловую систему. Это отдельный опасный этап: форматирование стирает прежнюю структуру. В этой инструкции нет команды форматирования, которую можно случайно применить к системному диску.

Закончилось место? Проверь также inode через df -i: могут закончиться записи для файлов, хотя байты ещё есть. Если df и du сильно расходятся, причиной могут быть открытые удалённые файлы или скрытые точки монтирования.

### Позже: дополнительные подробности

nofail в fstab позволяет загрузиться при недоступном подключении, но это подходит не всем ролям: без диска данных служба может начать писать на системный диск. Для постоянного хранилища отдельно проверяют зависимости служб.

### Где это находится

- /etc/fstab — Постоянные подключения файловых систем
- /srv/data — Пример точки подключения
- /dev/disk/by-uuid — Ссылки на устройства по UUID

### Команды и настройки

#### 1. Узнать, какие диски подключены

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает устройства, форматы, подключения, занятые байты и inode.

```bash
lsblk -o NAME,SIZE,FSTYPE,UUID,MOUNTPOINTS
findmnt /
df -hT
df -i
```

**Проверка:** Определи системный раздел по findmnt /, а не по догадке о /dev/sda.

#### 2. Образец строки fstab

**Формат:** Содержимое файла · Дополнительный шаг.

**Где:** В /etc/fstab, не в терминале. **Тип:** Образец конфигурации.

Объясняет шесть полей: источник, папка, тип, параметры, dump, порядок проверки.

**Это текст файла `/etc/fstab`. Его не выполняют напрямую в терминале.**

Открой файл на Linux:

```bash
SUDO_EDITOR=nano sudoedit /etc/fstab
```

Добавь фрагмент в существующий файл; сохрани остальные настройки.

Сохранение в nano: Ctrl+O (латинская O) → Enter → Ctrl+X. Затем выполни проверку из карточки.

```text
UUID=ФАКТИЧЕСКИЙ_UUID  /srv/data  ext4  defaults  0  2
```

**Проверка:** Только для УЖЕ существующей ext4-файловой системы с проверенным UUID; точка подключения должна быть подготовлена.

**Возврат / ограничения:** Сохрани копию /etc/fstab до изменения. Не перезагружайся с непроверенной строкой.

#### 3. Проверить fstab без перезагрузки

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Проверка конфигурации.

Проверяет записи fstab и сообщает о несоответствиях.

```bash
sudo findmnt --verify --verbose
```

**Проверка:** Это проверка файла, не полная гарантия загрузки. В учебной ВМ с консолью проверь адресное монтирование нужной точки и findmnt /srv/data.

#### 4. Найти крупные каталоги

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Оценивает размер подкаталогов /var в пределах файловой системы и объём журнала systemd.

```bash
sudo du -xhd1 /var
sudo journalctl --disk-usage
```

**Проверка:** Не удаляй файлы базы данных и не очищай /var/lib без разбора владельца данных.

### Наглядный обмен

**Как диск становится папкой**

1. Устройство → Файловая система: Устройство содержит раздел или файловую систему. Форматирование меняет структуру данных.
2. Файловая система → mount: mount связывает готовую файловую систему с местом в дереве.
3. mount → /srv/data: Приложения читают данные через обычную папку.
4. /srv/data → Устройство: fstab описывает, как снова подключить её при загрузке; запись нужно проверить.

### Микро-проверка

Что показывает df -h?

1. Все физические диски, включая пустые
2. Место в подключённых файловых системах
3. Только объём оперативной памяти

**Разбор:** Место в подключённых файловых системах. Для дерева устройств используют lsblk. df относится к смонтированным файловым системам.

## 11. Добавляем сайт: Nginx

**Уровень:** Практика

Сайт в первом упражнении — обычный HTML-файл. Nginx принимает запрос браузера, читает этот файл и отправляет его посетителю.

**Результат:** Windows получает именно страницу «Мой Linux-сервер работает», а не чужой сайт по умолчанию.

**Для практики сначала:** Установка программ и обновления, Службы и автозапуск, Файлы и права доступа.

**Цель:** Собрать локальный статический сайт и проверить его по всей цепочке.

**Параллель с Windows:** Это примерно роль IIS: веб-сервер принимает HTTP-запросы и отдаёт страницу либо передаёт запрос приложению.

Nginx — веб-сервер. В простом варианте он читает файл из папки сайта и отдаёт его браузеру. Для учебного сайта используем /srv/www/lab и имя lab.example.test, которое относится к тестовой зоне.

Практический порядок: создай папку и страницу → открой файл lab в редакторе → вставь описание сайта → сохрани → создай ссылку включения → выполни nginx -t → только при успехе reload → запрос с Windows. Команды и содержимое файла ниже подписаны отдельно.

На Ubuntu пакет Nginx обычно использует sites-available для описаний сайтов и sites-enabled для ссылок на включённые сайты. Такой порядок характерен для пакетной конфигурации Debian/Ubuntu и может отличаться на другой системе.

Директива root указывает папку файлов, server_name — имя сайта, listen — адрес и порт. Файлы должны быть доступны пользователю веб-службы; она обычно не должна иметь права менять содержимое статического сайта.

nginx -t проверяет синтаксис и возможность открыть необходимые файлы. После успешной проверки reload применяет настройки. Затем проверяют локальный ответ с правильным Host и с другого компьютера.

Учебный HTTP не защищает пароли. Для публичного сайта нужны настоящее имя, корректный DNS, TLS-сертификат и отдельный порядок выпуска. Имя .test и документационный IP не подходят для публичного сертификата.

### Где это находится

- /srv/www/lab/index.html — Файл учебной страницы
- /etc/nginx/sites-available/lab — Описание сайта
- /etc/nginx/sites-enabled/lab — Ссылка, включающая сайт
- /var/log/nginx — Журналы запросов и ошибок

### Команды и настройки

#### 1. Установить и создать страницу

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Добавляет веб-сервер и создаёт одну публично читаемую учебную страницу.

```bash
sudo apt install nginx
sudo install -d -m 755 /srv/www/lab
printf '%s\n' '<h1>Мой Linux-сервер работает</h1>' | sudo tee /srv/www/lab/index.html
sudo chmod 644 /srv/www/lab/index.html
```

**Проверка:** ls -l /srv/www/lab/index.html; nginx на Ubuntu может запуститься уже во время установки.

**Возврат / ограничения:** Сохрани необходимые данные; затем отключи только учебный сайт. Удалять общий пакет необязательно.

**Уточнение:** Папка /srv/www/lab должна быть новой; tee перезаписывает одноимённый файл.

#### 2. Описание сайта

**Формат:** Содержимое файла.

**Где:** В /etc/nginx/sites-available/lab. **Тип:** Образец конфигурации.

Указывает имя, порт и папку сайта. Не меняет настройки других сайтов.

**Это текст файла `/etc/nginx/sites-available/lab`. Его не выполняют напрямую в терминале.**

Открой файл на Linux:

```bash
SUDO_EDITOR=nano sudoedit /etc/nginx/sites-available/lab
```

Вставь в новый учебный файл. Если файл существует, сначала сохрани и разбери прежнее содержимое.

Сохранение в nano: Ctrl+O (латинская O) → Enter → Ctrl+X. Затем выполни проверку из карточки.

```text
server {
    listen 80;
    server_name lab.example.test;
    root /srv/www/lab;
    index index.html;
    location / {
        try_files $uri $uri/ =404;
    }
}
```

**Проверка:** Сохрани через sudoedit /etc/nginx/sites-available/lab. Это содержимое файла, не набор команд.

**Возврат / ограничения:** До изменения существующего файла сохрани его копию; для новой учебной конфигурации достаточно отключить её ссылку.

#### 3. Включить и проверить сайт

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Подключает новую конфигурацию и проверяет выбранный сайт по заголовку Host.

```bash
sudo ln -s /etc/nginx/sites-available/lab /etc/nginx/sites-enabled/lab
sudo nginx -t
sudo systemctl reload nginx
curl -H 'Host: lab.example.test' http://127.0.0.1
```

**Проверка:** Должен вернуться текст «Мой Linux-сервер работает». Если nginx -t сообщил ошибку, до reload не переходи. Строки «syntax is ok» и «test is successful» означают успешную проверку Nginx.

**Возврат / ограничения:** sudo unlink /etc/nginx/sites-enabled/lab; затем sudo nginx -t и sudo systemctl reload nginx.

**Уточнение:** Ссылку создают один раз. Если она уже есть, сначала проверь её. Команды выполняй по строке, продолжая только после успешной проверки.

#### 4. Проверить с Windows без изменения DNS

**Формат:** Команда Windows · PowerShell.

**Где:** В PowerShell на Windows. **Тип:** Сетевой запрос.

Только для этого запроса сопоставляет тестовое имя и адрес сервера.

**Подстановка:** Замени 192.0.2.10 на реальный IP своей ВМ; student — на имя своего пользователя. Вводить нужно в PowerShell на Windows.

```powershell
curl.exe --resolve lab.example.test:80:192.0.2.10 http://lab.example.test
```

**Проверка:** Замени IP на адрес ВМ. Должна вернуться именно твоя страница; отдельно нужны разрешённый TCP 80 и путь до сервера.

### Наглядный обмен

**Как Nginx отдаёт файл**

1. Браузер → Nginx :80: Браузер отправляет запрос и имя сайта в Host.
2. Nginx :80 → server_name: Nginx выбирает server-блок по адресу, порту и имени.
3. server_name → index.html: root связывает URL с папкой; права должны разрешать чтение.
4. index.html → Браузер: Файл возвращается клиенту. Ошибка 404 тоже означает, что HTTP-ответ получен, но запрошенный ресурс не найден.

**Как включается настройка**

1. sites-available → sites-enabled: В sites-enabled появляется ссылка на подготовленный файл.
2. sites-enabled → nginx -t: Nginx проверяет всю свою конфигурацию, а не только один новый файл.
3. nginx -t → reload: После успешной проверки выполняешь reload.
4. reload → sites-available: Проверяешь нужное имя сайта локально и с клиентского устройства.

### Микро-проверка

nginx -t сообщает ошибку. Что дальше?

1. Сразу restart
2. Исправить ошибку и снова проверить, затем применять

## 12. Своё приложение и HTTPS

**Уровень:** Дальше

Приложение само готовит ответ. Nginx встречает посетителя снаружи и передаёт его вопрос приложению внутри сервера.

**Результат:** Ответ Hello from Linux получен сначала напрямую, затем через Nginx.

**Для практики сначала:** Добавляем сайт: Nginx, Службы и автозапуск.

**Цель:** Понять service unit, отдельного пользователя и reverse proxy на маленьком примере.

**Параллель с Windows:** Похоже на отдельную Windows-службу приложения за IIS. Nginx принимает внешний запрос и передаёт его внутреннему процессу.

Статический сайт отдаёт готовые файлы. Приложение выполняет код: считает, читает базу и формирует ответ. Для него выделяют папку программы и отдельного пользователя с небольшими правами.

Обратный прокси принимает запрос клиента и передаёт его приложению. Приложение может слушать только 127.0.0.1:8000, а Nginx — внешний порт 80 или 443. Тогда внутренний порт не требуется открывать всему интернету.

Ниже минимальное учебное приложение Python: оно отвечает текстом и не публикует файлы каталога. Нужен пакет python3. Сначала создаём /opt/hello, затем файл server.py, затем unit, после чего включаем службу.

Параметры User и Group не дают процессу права root. NoNewPrivileges и ProtectSystem дополнительно ограничивают службу. Для настоящего приложения список ограничений проверяют по его потребностям, а секреты хранят вне кода и публичной папки.

Сначала получи обычный учебный HTTP-ответ на .test. Публичный HTTPS — следующий этап с настоящим доменом; его требования вынесены в «Позже».

### Позже: дополнительные подробности

TLS шифрует соединение и позволяет проверить сертификат сервера. Для публичного HTTPS нужны контролируемый домен, правильные A/AAAA-записи и проверка владения доменом. При HTTP-01 доступен порт 80; DNS-01 требует работы с DNS. Для .test публичный сертификат не выдаётся.

После настройки реального домена установи ACME-клиент по его официальной инструкции, запроси сертификат для своего имени и проверь автоматическое продление. У Certbot для Nginx это обычно certbot --nginx -d ТВОЙ_ДОМЕН; после установки проверь certbot renew --dry-run. Эта команда обращается к внешнему CA и требует настоящей подготовки.

## 13. Добавляем базу PostgreSQL

**Уровень:** Практика

База хранит записи, с которыми работает программа. Внутри базы свои пользователи и разрешения.

**Результат:** В новой labdb есть одна учебная запись; SELECT показывает её текст.

**Для практики сначала:** Установка программ и обновления, Пользователи и sudo.

**Цель:** Создать учебную базу и отдельную роль приложения без публикации порта наружу.

**Параллель с Windows:** По назначению это ближе к SQL Server. Пользователь ОС postgres и роли внутри PostgreSQL относятся к разным уровням.

База данных хранит структурированные данные и управляет их изменением. Приложению не выдают главного администратора базы: создают отдельную роль и отдельную БД с нужными полномочиями.

Пакет PostgreSQL в Ubuntu обычно создаёт один локальный кластер — работающий сервер БД со своими базами и настройками. Локальный вход может использовать peer: проверку по пользователю Linux. Для локального TCP обычно используется пароль SCRAM; действующие правила находятся в pg_hba.conf.

В примере labdb — новая учебная база, labapp — её пользователь внутри PostgreSQL, lesson_note — таблица, а одна строка в ней — наш тестовый текст. SQL — язык команд к базе; psql отправляет эти команды серверу БД.

Имя роли labapp в PostgreSQL не создаёт пользователя labapp в Linux. sudo -u postgres psql — запуск клиентской программы от системного пользователя postgres, после чего сервер базы отдельно проверяет свои правила.

listen_addresses определяет, где слушает PostgreSQL; pg_hba.conf — какие подключения и методы проверки разрешены. UFW — ещё один слой. В примере приложение и БД на одном сервере, поэтому внешний TCP 5432 не открываем.

Для копии работающей PostgreSQL используют её штатные инструменты, например pg_dump. Копировать /var/lib/postgresql обычным cp при запущенной БД — не равнозначная надёжная резервная копия.

### Где это находится

- /etc/postgresql/ВЕРСИЯ/main/postgresql.conf — Настройки кластера; версию смотри через pg_lsclusters
- /etc/postgresql/ВЕРСИЯ/main/pg_hba.conf — Правила допуска к БД
- /var/lib/postgresql — Файлы данных; вручную не удалять

#### 1. Установить и осмотреть кластер

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Ставит сервер и клиент, показывает реальный кластер и проверяет SQL-запрос.

## 14. Общая папка для Windows

**Уровень:** Практика

Samba делает папку Linux доступной в Проводнике Windows. Нужны и сетевой пароль, и права на саму папку.

**Результат:** Анна открыла ресурс project из Проводника и создала там учебный файл.

**Для практики сначала:** Пользователи и sudo, Файлы и права доступа, Сеть: адрес, маршрут и DNS.

**Цель:** Добавить ресурс с учётными записями, без гостевого доступа.

**Параллель с Windows:** Samba предоставляет общий ресурс SMB, который Windows открывает как сетевую папку.

Samba реализует SMB-доступ к папкам Linux. Путь в Windows выглядит как \\ИМЯ_СЕРВЕРА\project. Нужны одновременно: работающая служба, сетевой доступ, разрешённая учётная запись и права на файлы.

На Windows нажми Win+E: откроется Проводник. В его адресную строку, не в браузер, вводится путь \\АДРЕС_ВМ\project. При запросе учётных данных используй anna и пароль Samba, созданный через smbpasswd.

В уроке о правах мы создали Linux-пользователя anna, группу project и /srv/project. Для простого локального Samba-сервера добавляется отдельный пароль SMB через smbpasswd. Это не означает автоматическую синхронизацию паролей Linux и Samba.

valid users = @project ограничивает вход участниками группы. read only = no разрешает запись на уровне SMB, но не отменяет права Linux. Если папка запрещает запись этому пользователю, сетевой флажок ситуацию не исправит.

Разрешай SMB только в доверенной локальной сети или через VPN. Публиковать TCP 445 прямо в интернет для этого урока не требуется. В домене AD настройка идентичности и доступов отличается от этого локального примера.

create mask и directory mask ограничивают создаваемые разрешения, но итоговые права зависят и от запроса клиента, наследования и настроек Samba. Проверяй реальный файл, созданный из Windows.

### Где это находится

- /etc/samba/smb.conf — Описание общих ресурсов и настройки Samba
- /srv/project — Настоящая папка данных
- /var/log/samba — Журналы Samba

### Команды и настройки

#### 1. Установить и добавить SMB-пользователя

#### 2. Добавить секцию ресурса

**Формат:** Содержимое файла.

**Где:** Дополнение к /etc/samba/smb.conf. **Тип:** Образец конфигурации.

**Возврат / ограничения:** Верни прежний файл или убери только добавленную секцию project; снова testparm и перечитывание службы.

#### 3. Применить и ограничить сеть

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Перечитывает проверенную конфигурацию и показывает пример разрешения для доверенной сети.

**Подстановка:** Сначала подставь адреса и имя интерфейса своей ВМ. Значения 192.0.2.* относятся к документационным примерам.


**Проверка:** После успешного testparm и reload на Windows нажми Win+E, введи \\АДРЕС_ВМ\project, войди как anna и создай файл. На Linux ls -l /srv/project должен показать этот файл.

**Возврат / ограничения:** Удали только добавленное правило для своей подсети и верни исходную секцию ресурса.

**Уточнение:** Урок предполагает уже подготовленные /srv/project и группу project. Современный SMB по прямому адресу обычно использует TCP 445; обнаружение в сети — отдельная тема.

## 15. Копии и восстановление

**Уровень:** Практика

Копия нужна, чтобы вернуть потерянное. Создать архив — только половина задачи: потом проверяют возврат нужного файла или записи.

**Результат:** Файл вернулся в отдельную папку, а строка базы — в отдельную БД.

**Для практики сначала:** Файлы и права доступа, Добавляем сайт: Nginx, Добавляем базу PostgreSQL.

**Цель:** Скопировать файлы, отдельно сохранить базу и восстановить в другое место.

**Параллель с Windows:** По назначению это как резервное копирование Windows Server, но для разных типов данных могут понадобиться разные инструменты.

Резервная копия хранит возможность вернуться к предыдущему состоянию. Синхронизация и копия — разные вещи: команда с --delete может перенести удаление на вторую сторону. Снимок ВМ удобен перед опытом, но на том же хранилище не защищает от потери всего хоста.

Архив .tgz — сжатая упаковка файлов. Распаковка в /srv/restore-check создаст внутри неё srv/project: это учебная восстановленная копия, а не рабочая папка /srv/project. Для базы используем отдельную labdb_restore, чтобы сравнить строку и не перезаписать исходную БД.

Для учебного упражнения сохраняем /srv/project и настройки Nginx в /var/backups/linux-study. Такая копия на том же сервере помогает учиться, но не защищает от поломки диска и захвата сервера.

Для рабочей системы нужны несколько независимых копий, одна вне основного сервера, контролируемый доступ, защита секретов и понятный срок хранения. При необходимости копии шифруют, а ключ восстановления хранят отдельно.

Восстанавливай учебные файлы сначала в отдельный каталог. Проверь содержимое, права и работу приложения. Базы копируй штатным средством СУБД, а не обычным tar по работающему каталогу данных.

### Позже: дополнительные подробности

Укажи RPO — сколько последних изменений можно потерять, и RTO — за какое время надо восстановиться. Копия раз в сутки не обеспечивает потерю максимум пяти минут.

### Где это находится

- /var/backups/linux-study — Учебные архивы на этом же сервере
- /var/backups/pg-lab — Учебные выгрузки PostgreSQL, доступ только postgres
- /srv/restore-check — Отдельное место для проверки восстановления

### Команды и настройки

#### 1. Сохранить файлы и настройки

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Создаёт архив с относительными путями и показывает его содержимое.

```bash
sudo install -d -m 700 /var/backups/linux-study
sudo tar -czf /var/backups/linux-study/project-config.tgz -C / srv/project etc/nginx
sudo chmod 600 /var/backups/linux-study/project-config.tgz
sudo tar -tzf /var/backups/linux-study/project-config.tgz
```

**Проверка:** Нужны уже существующие /srv/project и /etc/nginx. Не архивируй активно меняющиеся данные как гарантированно согласованную копию.

**Возврат / ограничения:** При восстановлении сначала используй отдельную папку; не распаковывай в / поверх живого сервера.

**Уточнение:** Имя архива фиксированное и будет перезаписано. Это один учебный снимок файлов; расписание с отдельными именами — в следующем уроке.

#### 2. Пробно восстановить отдельно

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Распаковывает в отдельное место и сравнивает содержимое папки проекта.

```bash
sudo install -d -m 700 /srv/restore-check
sudo tar -xzf /var/backups/linux-study/project-config.tgz -C /srv/restore-check
sudo diff -r /srv/project /srv/restore-check/srv/project
```

**Проверка:** Восстанавливай только собственный доверенный архив. diff без вывода означает совпадение содержимого, но права и владельцев проверь через ls/stat отдельно.

**Возврат / ограничения:** Учебная копия находится в отдельном каталоге: рабочие файлы не затронуты.

#### 3. Сделать копию PostgreSQL

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Сохраняет согласованную логическую выгрузку одной БД в custom-формате. В неё входит таблица lesson_note с проверяемой строкой из блока PostgreSQL.

```bash
sudo install -d -o postgres -g postgres -m 700 /var/backups/pg-lab
sudo -u postgres pg_dump -Fc -f /var/backups/pg-lab/labdb.dump labdb
sudo -u postgres pg_restore --list /var/backups/pg-lab/labdb.dump
```

**Проверка:** Проверь код завершения и список объектов. Глобальные роли и внешние файлы приложения в pg_dump одной базы не входят.

**Уточнение:** Нужна база labdb из прошлого урока; имя файла фиксированное и будет перезаписано.

#### 4. Проверить восстановление БД

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Возвращает выгрузку в отдельную новую БД.

```bash
sudo -u postgres createdb --owner=labapp labdb_restore
sudo -u postgres pg_restore --exit-on-error --dbname=labdb_restore /var/backups/pg-lab/labdb.dump
sudo -u postgres psql -d labdb_restore -c 'SELECT * FROM lesson_note;'
```

**Проверка:** В новой labdb_restore должен вернуться id 1 и тот же текст «Моя первая запись». Это содержательная проверка возврата данных. Ошибка отсутствующей таблицы означает, что предыдущая учебная запись не вошла в копию.

**Возврат / ограничения:** Проверь результат, затем реши судьбу только учебной labdb_restore. Рабочую базу этот пример не перезаписывает.

**Уточнение:** labdb_restore должна отсутствовать до упражнения; повторный запуск требует осознанной работы с существующей копией.

## 16. Задачи по расписанию

**Уровень:** Дальше

Расписание запускает уже проверенную задачу в нужный момент. Сначала копируем руками, потом просим систему повторять это.

**Результат:** Одна ручная копия проверена, таймер включён, следующее время запуска видно.

**Для практики сначала:** Копии и восстановление, Службы и автозапуск.

**Цель:** Собрать понятную пару service + timer и проверить один запуск руками.

**Параллель с Windows:** systemd timer выполняет роль планировщика задач Windows. Таймер определяет когда, а service — что именно запускать.

Если ручная копия из прошлого блока ещё не работает, пока не включай расписание. Сначала один успешный ручной запуск и проверка восстановления; затем автоматизация.

Таймер systemd сам не содержит основную программу. Он активирует одноимённый service: project-backup.timer запускает project-backup.service. Для разового задания используется Type=oneshot.

Сначала подготовь и вручную проверь скрипт. Укажи полный путь к командам: окружение планировщика отличается от твоего терминала. Запуск по расписанию не должен ждать ввода пароля.

OnCalendar=*-*-* 03:00:00 задаёт ежедневное время. Без отдельного указания зоны оно трактуется в системном часовом поясе, который виден в timedatectl. RandomizedDelaySec добавляет небольшую задержку, чтобы задания не начинались все сразу.

Persistent=true позволяет наверстать пропущенное календарное срабатывание после включения таймера. Это не означает запуск каждой пропущенной копии по отдельности и не заменяет мониторинг ошибок.

В примере архивы получают разные имена; автоматического удаления старых копий нет. Для настоящей эксплуатации отдельно задают срок хранения, контроль места и перенос на независимое хранилище.

### Позже: дополнительные подробности

cron — другой распространённый планировщик. Он полезен для простых заданий, но у systemd timer удобно смотреть состояние и журнал через те же инструменты, что у служб. Не настраивай одну задачу одновременно в двух планировщиках.

### Где это находится

- /usr/local/sbin/project-backup — Локальный скрипт резервного копирования
- /etc/systemd/system/project-backup.service — Что выполнить
- /etc/systemd/system/project-backup.timer — Когда выполнить

### Команды и настройки

#### 1. Скрипт резервной копии

**Формат:** Содержимое файла.

**Где:** Содержимое /usr/local/sbin/project-backup. **Тип:** Код файла.

Сохраняет учебные данные с отдельным именем и проверяет читаемость архива. Нужны ранее созданные каталоги.

**Это текст файла `/usr/local/sbin/project-backup`. Его не выполняют напрямую в терминале.**

Открой файл на Linux:

```bash
SUDO_EDITOR=nano sudoedit /usr/local/sbin/project-backup
```

Вставь в новый учебный файл. Если файл существует, сначала сохрани и разбери прежнее содержимое.

Сохранение в nano: Ctrl+O (латинская O) → Enter → Ctrl+X. Затем выполни проверку из карточки.

```text
#!/bin/sh
set -eu
umask 077
/usr/bin/install -d -m 700 /var/backups/linux-study
archive="/var/backups/linux-study/project-$(/usr/bin/date -u +%Y%m%dT%H%M%SZ).tgz"
/usr/bin/tar -czf "$archive" -C / srv/project etc/nginx
/usr/bin/tar -tzf "$archive" >/dev/null
printf 'Backup ready: %s\n' "$archive"
```

**Проверка:** Создай файл через sudoedit, затем sudo chown root:root /usr/local/sbin/project-backup и sudo chmod 750 /usr/local/sbin/project-backup. Ручная проба: sudo /usr/local/sbin/project-backup.

**Возврат / ограничения:** Перед изменением прежнего скрипта сделай копию. Проверка списка архива не заменяет пробное восстановление.

#### 2. Описание задания

**Формат:** Содержимое файла.

**Где:** Содержимое project-backup.service. **Тип:** Образец конфигурации.

Запускает скрипт с правами чтения учебных данных и записи защищённого архива.

**Это текст файла `/etc/systemd/system/project-backup.service`. Его не выполняют напрямую в терминале.**

Открой файл на Linux:

```bash
SUDO_EDITOR=nano sudoedit /etc/systemd/system/project-backup.service
```

Вставь в новый учебный файл. Если файл существует, сначала сохрани и разбери прежнее содержимое.

Сохранение в nano: Ctrl+O (латинская O) → Enter → Ctrl+X. Затем выполни проверку из карточки.

```text
[Unit]
Description=Study project backup

[Service]
Type=oneshot
User=root
ExecStart=/usr/local/sbin/project-backup
```

**Проверка:** Сохрани через sudoedit /etc/systemd/system/project-backup.service. Скрипт и unit должны быть недоступны для записи обычным пользователям.

#### 3. Описание расписания

**Формат:** Содержимое файла.

**Где:** Содержимое project-backup.timer. **Тип:** Образец конфигурации.

Запускает одноимённый service каждый день с задержкой до пяти минут.

**Это текст файла `/etc/systemd/system/project-backup.timer`. Его не выполняют напрямую в терминале.**

Открой файл на Linux:

```bash
SUDO_EDITOR=nano sudoedit /etc/systemd/system/project-backup.timer
```

Вставь в новый учебный файл. Если файл существует, сначала сохрани и разбери прежнее содержимое.

Сохранение в nano: Ctrl+O (латинская O) → Enter → Ctrl+X. Затем выполни проверку из карточки.

```text
[Unit]
Description=Daily study project backup

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
RandomizedDelaySec=5m

[Install]
WantedBy=timers.target
```

**Проверка:** Сохрани через sudoedit /etc/systemd/system/project-backup.timer. timedatectl покажет используемый часовой пояс.

#### 4. Проверить ручной запуск и расписание

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Проверяет unit, запускает копию вручную, показывает журнал и включает расписание.

```bash
sudo systemd-analyze verify /etc/systemd/system/project-backup.service /etc/systemd/system/project-backup.timer
sudo systemctl daemon-reload
sudo systemctl start project-backup.service
sudo journalctl -u project-backup.service -n 30 --no-pager
sudo systemctl enable --now project-backup.timer
systemctl list-timers --all
```

**Проверка:** Сначала убедись, что ручной запуск успешен и новый архив восстанавливается. Только затем включай таймер и смотри NEXT.

**Возврат / ограничения:** sudo systemctl disable --now project-backup.timer. Уже запущенное задание этим не обязательно остановится.

**Уточнение:** Выполняй по строкам, переходя дальше после успешной проверки. Прочитай реальное время NEXT; оно зависит от часового пояса и случайной задержки.

### Наглядный обмен

**Когда и что**

1. Часы → project-backup.timer: Наступает запланированное время с учётом зоны и задержки.
2. project-backup.timer → project-backup.service: Timer запускает одноимённый service.
3. project-backup.service → Архив: Service вызывает заранее проверенный скрипт.
4. Архив → Часы: Проверяешь код завершения, свежесть копии, место и восстановление.

2. Таймер включён в автозапуск, результат задания проверяют отдельно

**Разбор:** Таймер включён в автозапуск, результат задания проверяют отдельно. Настроенное расписание не доказывает успешность задания и пригодность копии.

## 17. Журналы и поиск причины

**Уровень:** Основа

Поиск причины — цепочка коротких вопросов. Что не отвечает? Работает ли программа? Есть ли у неё доступ к файлу?

**Результат:** Ты можешь собрать наблюдения по одному сбою и отделить факт от догадки.

**Для практики сначала:** Службы и автозапуск.

**Цель:** Искать причину отказа по фактам и времени, а не перезапускать всё подряд.

**Параллель с Windows:** journalctl похож по назначению на просмотр событий Windows. ss показывает соединения и порты, а top/htop — процессы.

Начни с вопроса: что именно не работает, у кого и с какого времени? Сайт может не открываться из-за имени, маршрута, firewall, службы, приложения или БД. Одно сообщение «не работает сервер» ещё ничего не локализует.

Журнал хранит сообщения программ и системы. journalctl -u hello показывает одну службу; -b ограничивает текущей загрузкой; --since и --until задают период. Сопоставляй часовые пояса клиента и сервера.

Названия ошибок не надо запоминать все сразу. Открой стартовую памятку: там переведены Permission denied, command not found, Connection refused и основные HTTP-коды. В каждой проверке ищи один ответ на один вопрос.

Проверяй последовательно: 1) правильный узел и время; 2) ресурсы и место; 3) состояние службы и журнал; 4) локальный ответ; 5) порт и firewall; 6) запрос с клиента; 7) DNS/TLS и права приложения.

Мониторинг заранее сообщает о проблеме: HTTP-проверка снаружи, место и inode, срок TLS, состояние копий, ошибки служб. Выбирай оповещения, на которые есть конкретное действие. Сбор метрик без реакции не решает проблему.

Перед изменением зафиксируй исходное состояние и гипотезу. Меняй один фактор и снова проверяй ту же функцию с того же клиента. Успешный restart без найденной причины не объясняет, почему случился отказ.

### Позже: дополнительные подробности

Высокая load average не равна проценту занятого CPU: она отражает число задач, ожидающих процессор или находящихся в непрерываемом ожидании. Мало free-памяти тоже не всегда проблема: Linux использует память под кеш; смотри available и признаки давления.

### Где это находится

- /var/log — Журналы файловых подсистем и приложений
- /var/log/nginx/error.log — Ошибки Nginx в типовой пакетной конфигурации
- /etc/systemd/journald.conf.d — Дополнения политики хранения журнала

### Команды и настройки

#### 1. Быстрый обзор здоровья

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает время, нагрузку, память, место, inode и проблемные unit.

```bash

uptime
free -h
df -h
df -i
systemctl --failed
```

**Проверка:** Записывай наблюдение со временем; не выдавай одну цифру за доказанную причину.

#### 2. Журнал за последний час

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает службу, предупреждения текущей загрузки и доступную глубину истории.

```bash
sudo journalctl -u hello --since '-1 hour' --no-pager
sudo journalctl -p warning -b -n 80 --no-pager
sudo journalctl --list-boots
```

**Проверка:** Если нужной загрузки нет, не делай вывод, что ошибок тогда не было. История могла не сохраняться.

#### 3. От локального ответа к клиенту

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Чтение и локальный запрос.

Сопоставляет порт, ответ Nginx и журнал его ошибок.

```bash
sudo ss -lntp
curl --connect-timeout 5 -H 'Host: app.example.test' http://127.0.0.1
sudo tail -n 40 /var/log/nginx/error.log
```

**Проверка:** Если с сервера ответ есть, а с клиента нет, переходи к привязке адреса, firewall и внешнему пути. При 502 проверь внутреннее приложение.

### Наглядный обмен

**Лестница диагностики**

1. Клиент и DNS → Сеть и порт: Проверяешь правильное имя, IP и достижимость нужного TCP-порта.
2. Сеть и порт → Служба: Есть ли слушающая программа и что пишет её журнал?
3. Служба → Данные и права: Программа может работать, но не иметь доступа к файлу или базе.
4. Данные и права → Клиент и DNS: После точечного исправления проверяешь исходную задачу того же пользователя.

### Микро-проверка

Сервер отвечает на ping. Это доказывает, что сайт исправен?

1. Да
2. Нет, отдельно проверяют TCP, TLS/HTTP и приложение
3. Да, если ping быстрый

**Разбор:** Нет, отдельно проверяют TCP, TLS/HTTP и приложение. ICMP проверяет только часть пути; сайт зависит от других уровней.

## 18. Контейнеры без путаницы

**Уровень:** Дальше

Образ — коробка с готовой программой. Контейнер — запущенная программа из этой коробки. Постоянные данные хранят отдельно.

**Результат:** Учебный контейнер отвечает на локальном 8080, после упражнения остановлен только он.

**Для практики сначала:** Установка программ и обновления, Сеть: адрес, маршрут и DNS, Копии и восстановление.

**Цель:** Запустить локальный пример и понимать, куда пропадают данные.

**Параллель с Windows:** Контейнер похож на упакованный запуск программы, но не является отдельной полноценной виртуальной машиной.

Образ — готовый шаблон файлов программы. Из него запускают контейнер — работающий экземпляр. Как одна установочная коробка и несколько отдельно запущенных программ: получить коробку и запустить программу — разные действия.

В Ubuntu есть пакет docker.io из репозитория Ubuntu. У Docker есть и собственный репозиторий с другими именами пакетов. Для учебного примера выбираем один путь — docker.io — и не смешиваем инструкции установки.

Ключ -p сопоставляет порт хоста и порт внутри контейнера. Запись 127.0.0.1:8080:80 публикует внутренний 80 только на loopback хоста. Простое 8080:80 часто открывает доступ шире, чем ожидает новичок.

Том или явно подключённая папка хранит постоянные данные вне временного слоя контейнера. Пересоздание контейнера не должно удалять единственную копию БД. Наличие volume ещё не является резервной копией.

Доступ к Docker daemon и членство в группе docker дают очень широкое управление хостом. Для первых упражнений используй отдельный sudo на команду и не добавляй всех пользователей в docker.

Образ nginx:stable удобен для знакомства, но тег изменяемый. Для воспроизводимого рабочего развёртывания фиксируют версию или digest, проверяют источник и отдельно планируют обновление и копии. Compose помогает описать несколько сервисов, сетей и томов в одном файле.

### Позже: дополнительные подробности

Контейнеры на Linux используют ядро хоста. Docker daemon и группа docker дают широкие полномочия, поэтому это не такая же граница безопасности, как отдельная виртуальная машина.

### Где это находится

- /var/lib/docker — Управляемые Docker данные; не очищать вручную
- compose.yaml — Описание набора сервисов в Docker Compose
- 127.0.0.1:8080:80 — Хост loopback:порт хоста:порт контейнера

### Команды и настройки

#### 1. Установить один выбранный Docker

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Устанавливает Docker из уже настроенных репозиториев Ubuntu.

```bash
sudo apt install docker.io
sudo systemctl enable --now docker
sudo docker version
```

**Проверка:** Сначала проверь, что на учебной ВМ нет другой установки Docker и рабочих контейнеров.

**Возврат / ограничения:** Остановить только учебный контейнер можно отдельно; отключать весь Docker на общем сервере нельзя без разбора зависимостей.

#### 2. Запустить сайт только локально

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Меняет настройки.

Загружает образ, если его нет, и запускает временный веб-контейнер только для локального доступа.

```bash
sudo docker run --rm -d --name lab-container -p 127.0.0.1:8080:80 nginx:stable
curl -I http://127.0.0.1:8080
sudo docker ps
sudo docker logs lab-container
```

**Проверка:** Нужен интернет для загрузки образа. curl должен получить HTTP-ответ. Проверь именно loopback-привязку.

**Возврат / ограничения:** sudo docker stop lab-container. Из-за --rm контейнер удалится после остановки; образ останется.

**Уточнение:** Показан временный контейнер без постоянных данных. На сервере с UFW отдельно проверь правила Docker и внешнюю доступность.

### Наглядный обмен

**Четыре разные сущности**

1. Образ → Контейнер: Из одного образа можно запустить несколько экземпляров.
2. Порт хоста → Контейнер: Сопоставление портов даёт путь к программе внутри контейнера.
3. Контейнер → Том: Постоянные данные направляют в специально выбранное хранилище.
4. Образ → Том: Замена контейнера новым образом не заменяет план миграции и резервного копирования данных.

### Микро-проверка

Что публикует -p 127.0.0.1:8080:80?

1. Порт 80 на всех внешних адресах
2. Внутренний 80 на локальном 8080 хоста
3. SSH на 8080

**Разбор:** Внутренний 80 на локальном 8080 хоста. Первый адрес ограничивает привязку loopback-интерфейсом, 8080 — порт хоста, 80 — порт контейнера.

- [ ] Проверить локальную привязку порта
- [ ] Остановить только свой учебный контейнер

## 19. Обслуживание и защита

**Уровень:** Практика

Защита начинается с простых вещей: отдельные учётные записи, нужные порты, обновления и рабочие копии.

**Результат:** Записано, кто имеет доступ, что открыто по сети и когда проверяют копии.

**Для практики сначала:** Вход с Windows по SSH, Firewall и открытые порты, Копии и восстановление.

**Цель:** Составить повторяемый режим работы вместо разовой настройки.

**Параллель с Windows:** По смыслу это политика обновлений, минимальные права, защита служб и план обслуживания Windows Server.

Начни с минимального набора служб, личных учётных записей, проверенного SSH-доступа, ограниченной сети и резервных копий. Сложный инструмент не заменяет эти основы.

Для первого сервера запиши четыре регулярные проверки: открывается ли нужный сервис, хватает ли места, свежая ли копия и удавалось ли из неё восстановиться. Затем добавляй более сложные инструменты.

AppArmor ограничивает действия отдельных программ сверх обычных прав файлов. В Ubuntu сначала посмотри существующие профили и события отказа. При ошибке не отключай защиту всей системы: выясни, какое действие и какой профиль её вызвал.

Автоматические обновления настраивают осознанно. На Ubuntu часто используется unattended-upgrades, но наличие пакета не доказывает активную политику. Проверь реальные конфиги и журналы. Автоматическую перезагрузку согласуют отдельно.

Секреты — пароли, закрытые ключи и токены — хранят вне публичных папок и репозиториев. Выдавай их только нужной службе, ограничивай чтение и предусматривай смену. Значения секретов не должны попадать в журнал и снимки экрана.

Раз в день полезно контролировать доступность и ошибки копирования, раз в неделю — обновления и место, периодически — доступы, срок TLS, восстановление и устаревшие службы. Частота зависит от важности системы.

### Позже: дополнительные подробности

Astra Linux, ALT и RHEL-подобные системы могут добавлять другие модели контроля доступа и процессы сертификации. Там Ubuntu-команды не являются готовой политикой эксплуатации; сверяй документацию своей редакции.

### Где это находится

- /etc/apt/apt.conf.d — Фактическая политика apt и unattended-upgrades
- /etc/apparmor.d — Профили AppArmor
- /var/log/unattended-upgrades — Журналы автоматических обновлений
- /etc/ssh/sshd_config.d — Политика доступа SSH

### Команды и настройки

#### 1. Осмотреть защиту и задачи обновления

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Показывает AppArmor, расписания, пакет обновлений и поверхность сетевого доступа.

```bash

systemctl list-timers --all
apt-cache policy unattended-upgrades
sudo ss -lntup
```

**Проверка:** Отсутствие aa-status может означать, что утилита не установлена. Наличие профиля или таймера не доказывает полноту защиты.

#### 2. Проверить политику автоматических обновлений

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Читает настройки и доступный журнал. Закомментированные строки отличаются от действующих.

```bash
sudo grep -R -n -E 'APT::Periodic|Automatic-Reboot|Allowed-Origins' /etc/apt/apt.conf.d
sudo journalctl -u unattended-upgrades --since '-7 days' --no-pager
```

**Проверка:** Учитывай порядок файлов apt.conf.d и настройки в других файлах. Политику перезагрузки не меняй по одной найденной строке.

**Рабочий цикл обслуживания**

2. Подготовить → Изменить: Сохраняешь изменяемые настройки и проверяешь путь восстановления.

## 20. Собираем свой сервер

**Уровень:** Итог

Собираем знания в одну понятную систему: кто входит, что работает, как увидеть сбой и как вернуть данные.

**Результат:** У учебного сервера есть карточка, проверка с Windows и проверенное восстановление.

**Для практики сначала:** Вход с Windows по SSH, Добавляем сайт: Nginx, Копии и восстановление, Журналы и поиск причины.

**Цель:** Получить критерии готовности и понимать следующий шаг обучения.

**Параллель с Windows:** Похоже на создание небольшой серверной инфраструктуры: роли, доступы, наблюдение и восстановление связаны между собой.

Учебный итог: отдельная ВМ с личным администратором, входом по ключу, ограниченными портами, сайтом или приложением, отдельной БД, общим ресурсом для доверенной сети и проверенным восстановлением.

Итог не в том, чтобы установить все роли сразу. Выбери одну полезную задачу, например сайт или общую папку, пройди для неё всю цепочку и только потом добавляй следующую.

Не обязательно держать все роли на одной машине. В уроках это удобно для знакомства; в рабочей инфраструктуре роли разделяют по требованиям к безопасности, нагрузке и отказоустойчивости.

Для каждой роли запиши шесть вещей: назначение, пакет и версия, конфигурация и данные, учётная запись процесса, сетевой доступ, способ проверки и восстановления. Такая карточка полезнее списка случайных команд.

Следующий уровень — Ansible для повторяемой настройки, VPN для защищённого административного доступа, централизованные метрики и журналы, управление секретами и тестирование восстановления на чистой машине.

Другие роли: DNS — например BIND; DHCP — например Kea; NFS — общие файлы между Linux; VPN — WireGuard; каталог пользователей — AD-интеграция или FreeIPA; почта — отдельная сложная система. Их не добавляют «на всякий случай»: каждой роли нужны своя политика, сеть и копии.

Когда что-то забывается, возвращайся к четырём вопросам: что выполняет задачу, где его настройка, где его данные и чем я докажу, что оно работает. После этого нужная команда обычно находится гораздо легче.

### Где это находится

- Карточка узла — Имя, ОС, назначение, адреса, владелец; без секретов
- Карточка роли — Пакеты, файлы, учётная запись, порты и проверки
- Журнал изменений — Дата, исходное состояние, действие, проверка, откат

### Команды и настройки

#### 1. Итоговый осмотр

**Формат:** Команда Linux · терминал сервера.

**Где:** На учебном Linux-сервере. **Тип:** Только чтение.

Собирает итоговую картину учебного сервера.

```bash
hostnamectl
systemctl --failed
sudo ss -lntup
df -h
df -i
systemctl list-timers --all
```

**Проверка:** Затем с Windows проверь реальную страницу и общий ресурс; отдельно проверь копию и восстановление.

### Наглядный обмен

**Что означает готовность**

1. Доступ → Работа роли: Новый вход администратора и обычный доступ пользователя проверены.
2. Работа роли → Наблюдение: Нужный клиент получает правильный ответ, а не просто открытый порт.
3. Наблюдение → Восстановление: Ошибки обнаруживаются, а копии создаются и контролируются.
4. Восстановление → Доступ: Данные реально возвращались из копии, а путь восстановления записан.

### Микро-проверка

Что лучше подтверждает готовность роли?

1. Пакет установлен
2. Нужный клиент выполнил задачу, а наблюдение и восстановление проверены
3. В конфиге много строк

**Разбор:** Нужный клиент выполнил задачу, а наблюдение и восстановление проверены. Нужен проверенный результат и возможность сопровождения роли.

## Учебные расследования

### Сайт не запускается

После изменения сайта Nginx перестал запускаться. Собери два свидетельства, выбери причину и проверь учебное исправление.

Команды-наблюдения:

- systemctl status nginx
- sudo nginx -t
- sudo journalctl -u nginx -n 20

**Причина в модели:** Состояние failed и точная ошибка nginx -t указывают на неверный конфигурационный файл.

**Действие в модели:** Убрать лишнюю скобку в учебном файле, повторить nginx -t и запустить Nginx.

**Проверка:** Браузер учебного клиента получил HTTP 200 и страницу lab.example.test.

### Страница отвечает 403

Nginx работает, но страница запрещена. Разберись с доступом к папке; открывать всем запись не требуется.

Команды-наблюдения:

- curl -I http://127.0.0.1
- namei -l /srv/www/lab/index.html
- id www-data

**Причина в модели:** HTTP-ответ уже есть. Каталог lab разрешает проход только root, а Nginx работает от www-data.

**Действие в модели:** Дать чтение и проход в публичную учебную папку lab без права записи остальным.

**Проверка:** Повторный запрос клиента вернул HTTP 200. Публичный каталог не стал доступен всем для записи.

### Сервер видит сайт, Windows — нет

В этой вымышленной сети адрес и внешний путь уже проверены. На самом сервере страница отвечает, а клиент не устанавливает TCP.

Команды-наблюдения:

- curl -I http://127.0.0.1
- sudo ss -lntp
- sudo ufw status

**Причина в модели:** Рабочий локальный ответ, внешняя привязка Nginx и отсутствие разрешения 80 в UFW локализуют проблему в рамках этой модели.

**Действие в модели:** Добавить разрешение TCP 80, сохранив действующее правило SSH.

**Проверка:** Учебный клиент теперь установил TCP 80 и получил нужную страницу. В реальности внешний путь проверяют отдельно.

### Место есть, файлы не создаются

Приложение сообщает No space left on device, хотя свободные гигабайты ещё есть.

Команды-наблюдения:

- df -h
- df -i
- sudo du -xhd1 /var

**Причина в модели:** df -i показывает 100%, а каталог учебного кеша известен как источник множества одноразовых файлов.

**Действие в модели:** Остановить генерацию кеша, убрать только устаревшие учебные миниатюры и ограничить их хранение.

**Проверка:** Новый учебный файл создан, df -i больше не заполнен. В реальности перед очисткой выясняют владельца и назначение данных.

### По имени не находится

У учебного сервера есть адрес и маршрут, но curl не может найти имя example.com.

Команды-наблюдения:

- ip route
- resolvectl status
- resolvectl query example.com

**Причина в модели:** Факты указывают на недоступный DNS в этой модели. Они не доказывают отсутствие других проблем после его исправления.

**Действие в модели:** Исправить DNS в управляемой конфигурации учебной сети, проверить и применить через консоль.

**Проверка:** Учебное имя разрешается; отдельный HTTP-запрос тоже успешен. Это два разных результата.

### Nginx отвечает 502

Прокси доступен, но приложение за ним не отвечает. Найди недостающий компонент.

Команды-наблюдения:

- curl -I http://127.0.0.1
- systemctl status hello
- sudo ss -lntp

**Причина в модели:** Nginx уже возвращает HTTP-ответ, а процесс upstream отсутствует и unit inactive.

**Действие в модели:** Запустить проверенную службу hello и включить её автозапуск.

**Проверка:** Запрос через Nginx вернул Hello from Linux, а не просто открытый порт.

### Копии по расписанию нет

Описание таймера создано, но файлов новых копий не появляется. Задача ещё не включена.

Команды-наблюдения:

- systemctl list-timers --all
- systemctl is-enabled project-backup.timer
- systemctl status project-backup.service

**Причина в модели:** Таймер disabled. Успешно завершившийся oneshot может быть inactive — это не то же самое, что failed.

**Действие в модели:** Проверить ручную копию и восстановление, затем enable --now для таймера.

**Проверка:** Учебный запуск завершился успешно, появилась новая копия, пробное восстановление совпало.

### Архив есть — верни файл

В модели сотрудник изменил документ. Архив существует; нужно доказать, что из него возвращается нужный текст.

Команды-наблюдения:

- sudo tar -tzf /var/backups/linux-study/project-config.tgz
- cat /srv/project/plan.txt
- ls -ld /srv/restore-check

**Причина в модели:** Наличие имени в архиве ещё не доказывает восстановление. Сначала нужна отдельная проверка без перезаписи живых данных.

**Действие в модели:** Создать отдельный каталог и вернуть туда собственный доверенный архив.

**Проверка:** Проверено: в восстановленном файле «Встреча в 10:00», владелец и права ожидаемые. Возврат в рабочую папку — отдельное осознанное действие.


## Словарь

### Ядро

Часть ОС, которая управляет процессами, памятью, устройствами и базовыми правами.

Пример: Как диспетчер, который распределяет оборудование между программами.

### Дистрибутив

Готовая система на основе Linux: ядро, программы, установщик, репозитории и правила сопровождения.

Пример: Ubuntu, Debian, AlmaLinux, Astra Linux и ALT — разные дистрибутивы.

### Служба

Программа, которую система запускает для постоянной работы или по запросу.

Пример: Nginx обслуживает запросы к сайту без открытого окна терминала.

### Пакет

Набор файлов программы с описанием версии, зависимостей и установки.

Пример: apt install nginx устанавливает пакет Nginx и нужные зависимости.

### Конфигурация

Настройки, по которым программа выбирает своё поведение.

Пример: В конфигурации Nginx задают папку сайта и порт.

### Снимок ВМ

Сохранённое состояние виртуальной машины в конкретный момент по правилам гипервизора.

Пример: Помогает вернуть учебную ВМ перед неудачной правкой; не заменяет независимую копию.

### Терминал

Окно, в котором вводят текстовые команды и читают ответы программ.

Пример: Windows Terminal может открыть SSH-сеанс Linux.

### Оболочка

Программа, которая разбирает команды, подставляет переменные и запускает другие программы.

Пример: Bash — распространённая оболочка в Linux; PowerShell — другая оболочка.

### root

Учётная запись с UID 0 и широкими правами управления ОС.

Пример: Обычной службе сайта почти никогда не нужен постоянный запуск от root.

### sudo

Средство выполнить разрешённую команду от другого пользователя, обычно root.

Пример: sudoedit /etc/hosts позволяет редактировать системный файл.

### UID

Числовой идентификатор пользователя, который ОС использует при проверке прав.

Пример: Владелец файла хранится как UID, а имя отображается через справочник пользователей.

### Группа

Набор пользователей для назначения общих прав.

Пример: Группа project получает доступ к /srv/project.

### Владелец

Пользователь и группа, записанные в свойствах файла или папки.

Пример: chown root:project задаёт владельца root и группу project.

### umask

Маска, которая убирает часть разрешений при обычном создании объектов.

Пример: umask 077 обычно ограничивает новые личные файлы владельцем; итог зависит также от программы и ACL.

### ACL

Дополнительный список разрешений для конкретных пользователей или групп.

Пример: Позволяет дать одному сотруднику чтение, не добавляя его в основную группу.

### Репозиторий пакетов

Настроенный источник пакетов и подписанных сведений о версиях.

Пример: apt update загружает списки из подключённых источников Ubuntu.

### Зависимость

Другой компонент, необходимый программе.

Пример: Пакет может требовать конкретную библиотеку; пакетный менеджер учитывает это.

### SSH

Протокол защищённого удалённого входа и выполнения команд.

Пример: ssh student@адрес открывает терминал на сервере.

### SSH-ключ

Пара открытого и закрытого ключей для проверки владения ключом.

Пример: Открытый ключ отправляют на сервер; закрытый оставляют на клиенте.

### Отпечаток

Короткое представление открытого ключа для сверки личности узла.

Пример: Сверь отпечаток SSH-сервера по доверенной консоли при первом входе.

### systemd

Система запуска и управления службами и другими ресурсами в выбранной Ubuntu.

Пример: systemctl управляет unit, journalctl читает журнал.

### Unit

Именованный объект systemd: служба, таймер, сокет и другие типы.

Пример: hello.service запускает приложение, project-backup.timer определяет расписание.

### daemon-reload

Перечитывание описаний unit-файлов systemd.

Пример: После правки hello.service нужен daemon-reload, а для перезапуска программы — отдельное действие.

### Сетевой интерфейс

Точка подключения ОС к реальной или виртуальной сети.

Пример: enp1s0 — пример имени; у твоей ВМ оно может быть другим.

### Префикс сети

Число бит адреса, описывающих сеть.

Пример: У обычной IPv4-подсети /24 маска 255.255.255.0; адреса сети и broadcast имеют отдельное назначение.

### Шлюз

Следующий узел маршрута к другим сетям.

Пример: Default route часто ведёт к роутеру или виртуальному шлюзу хостинга.

### DNS

Система поиска записей по доменным именам, включая IP-адреса.

Пример: Имя example.com сначала разрешается в адрес, затем начинается соединение.

### Netplan

Средство описать сеть Ubuntu в YAML и передать настройки сетевому backend.

Пример: netplan generate проверяет и генерирует конфигурацию; try позволяет пробное применение.

### YAML

Текстовый формат со структурой, зависящей от отступов.

Пример: В Netplan используют пробелы, а не табуляции.

### Порт

Числовой идентификатор сетевой точки входа в приложении.

Пример: TCP 22 обычно SSH; TCP 443 обычно HTTPS. Номер сам по себе не доказывает протокол.

### Слушающий сокет

Ожидание входящих соединений программой на конкретном адресе и порту.

Пример: ss -lntp покажет, где процесс слушает TCP.

### Firewall

Правила, разрешающие или запрещающие сетевой обмен.

Пример: Разрешённый TCP 80 не запускает веб-сервер.

### UFW

Удобный инструмент управления firewall в Ubuntu.

Пример: ufw status verbose показывает его политики и правила.

### Loopback / localhost

Локальная сеть внутри самого узла: обычно 127.0.0.1 и ::1.

Пример: Приложение на 127.0.0.1:8000 напрямую недоступно с другого компьютера.

### NAT

Изменение сетевых адресов при прохождении через узел.

Пример: Сервер за роутером может видеть другой адрес источника, чем адрес Windows в локальной сети.

### Диск

Физическое или виртуальное блочное устройство для хранения данных.

Пример: У одной ВМ может быть системный диск и отдельный диск данных.

### Файловая система

Структура, которая хранит файлы, каталоги и метаданные на устройстве.

Пример: ext4 — распространённый вариант в Linux.

### Монтирование

Подключение файловой системы к папке в общем дереве Linux.

Пример: Диск данных доступен через /srv/data вместо отдельной буквы D:.

### fstab

Файл описания постоянных подключений файловых систем.

Пример: Ошибочная обязательная запись может мешать загрузке; сначала проверяют конфигурацию.

### UUID файловой системы

Идентификатор, который помогает найти нужную файловую систему без привязки к имени устройства.

Пример: UUID в fstab обычно надёжнее предположения, что диск всегда будет /dev/sdb.

### inode

Запись с метаданными объекта файловой системы.

Пример: Из-за огромного числа мелких файлов могут закончиться inode при свободных гигабайтах.

### Nginx

Веб-сервер и обратный прокси.

Пример: Может отдавать index.html или передавать запрос приложению на 127.0.0.1.

### Host / имя сайта

Имя, которое клиент сообщает HTTP-серверу для выбора сайта.

Пример: curl -H 'Host: lab.example.test' проверяет конкретный server_name локально.

### Обратный прокси

Сервер перед приложением, который принимает запрос и передаёт его внутреннему обработчику.

Пример: Nginx :443 → приложение 127.0.0.1:8000.

### TLS

Протокол защиты соединения и проверки сертификата сервера.

Пример: HTTPS — HTTP поверх TLS. Шифрование не исправляет уязвимости самого приложения.

### Сертификат

Документ, связывающий открытый ключ с именем и подписанный доверенным издателем.

Пример: Браузер проверяет имя, срок и доверие к цепочке; закрытый ключ хранится отдельно.

### База данных / СУБД

СУБД — программа, которая хранит и обрабатывает структурированные данные.

Пример: PostgreSQL обслуживает базы, роли и SQL-запросы.

### Peer-аутентификация

Метод локальной проверки PostgreSQL по имени пользователя ОС.

Пример: sudo -u postgres psql часто работает через локальный Unix-сокет и peer.

### pg_hba.conf

Правила, выбирающие допустимые подключения и метод аутентификации PostgreSQL.

Пример: Адрес, имя БД, роль и порядок строк имеют значение.

### Samba / SMB

Samba — программная реализация SMB-доступа, которым пользуется Windows для общих папок.

Пример: Для записи нужны разрешения SMB и права Linux на саму папку.

### Резервная копия

Независимая возможность вернуть данные к нужному состоянию.

Пример: Хорошая проверка — вернуть копию в отдельное место и открыть данные.

### RPO

Допустимый объём потери последних изменений, выраженный временем.

Пример: Копия раз в сутки может означать потерю почти суток изменений.

### RTO

Целевое время восстановления работоспособности.

Пример: Надо измерить, успеешь ли вернуть систему в требуемый срок.

### Таймер systemd

Unit, который активирует другой unit по времени.

Пример: project-backup.timer запускает project-backup.service.

### cron

Планировщик периодических команд.

Пример: Для задания выбирают либо cron, либо timer, чтобы не запустить его дважды.

### Скрипт

Файл с последовательностью команд или кодом.

Пример: Скрипт копирования сначала проверяют вручную, затем добавляют в расписание.

### Журнал

Сообщения системы и программ с отметками времени.

Пример: journalctl -u hello показывает сообщения выбранной службы.

### Load average

Среднее число задач, выполняющихся или ожидающих CPU и некоторых видов ввода-вывода.

Пример: Значение оценивают вместе с числом CPU, процессами и ожиданием диска.

### Мониторинг

Регулярное наблюдение за состоянием и уведомление о значимых отклонениях.

Пример: Снаружи проверяют HTTP, внутри — ресурсы, службы и свежесть копий.

### Образ контейнера

Шаблон файлов и параметров для запуска контейнера.

Пример: Один nginx:stable позволяет создать несколько контейнеров; тег может измениться.

### Контейнер

Изолированный запуск процесса с окружением, использующий ядро хоста.

Пример: Удаление контейнера может потерять данные его записываемого слоя.

### Том контейнера

Выделенное хранилище для данных за пределами временного слоя контейнера.

Пример: Данные переживают пересоздание контейнера при правильном подключении тома; копия всё равно нужна.

### AppArmor

Дополнительные ограничения действий программы на основе профиля.

Пример: Сначала изучают конкретное запрещённое действие, а не отключают защиту целиком.

### Автоматические обновления

Установка выбранных обновлений по заданной политике.

Пример: unattended-upgrades требует проверки настроек, журналов и политики перезагрузки.

### Ansible

Инструмент повторяемой настройки узлов по описанным задачам.

Пример: Удобен после понимания ручной цепочки установки, конфигурации и проверки.

### VPN

Защищённый сетевой путь между участниками через другую сеть.

Пример: Администрирование и SMB удобно ограничивать доверенной VPN-сетью вместо публикации наружу.

### Идемпотентность

Свойство повторного действия не менять уже достигнутое нужное состояние.

Пример: Для автоматизации важно описывать состояние, а не многократно добавлять одинаковую строку.

### Виртуальная машина / ВМ

Отдельный виртуальный компьютер внутри другого компьютера, со своей ОС и виртуальными дисками.

Пример: Можно учиться в Ubuntu-ВМ, не заменяя Windows на основном компьютере.

### ISO-образ

Файл с содержимым установочного диска.

Пример: Его подключают к виртуальному приводу для установки Ubuntu, затем отключают, чтобы загрузиться с установленной системы.

### Роль сервера

Конкретная задача, которую сервер выполняет для пользователей или программ.

Пример: Сайт, файловая папка и база данных — разные роли, хотя их можно изучать на одной ВМ.

### Аргумент команды

Данные, которые сообщают программе, что именно обрабатывать.

Пример: В cat notes.txt название notes.txt — аргумент.

### Параметр / флаг команды

Дополнительная настройка запуска программы.

Пример: В ls -lah параметр -a просит показать также скрытые имена, -l — подробности, -h — удобные размеры.

### Канал / символ |

Передача текстового вывода одной команды на вход другой.

Пример: sshd -T | grep … оставляет только нужные строки конфигурации.

### Перенаправление > и >>

Запись вывода в файл. > может заменить прежнее содержимое, >> дописывает.

Пример: Не меняй > и >> местами, особенно в системных командах.

### DHCP

Служба, которая выдаёт устройству сетевые настройки автоматически.

Пример: Резервация на DHCP-сервере позволяет выдавать одному узлу один и тот же адрес.

### setgid на каталоге

Флажок, который помогает новым файлам и папкам наследовать группу родительского каталога.

Пример: В chmod 2770 первая 2 включает setgid, а 770 задаёт базовые права.

### Sticky bit

Дополнительное ограничение удаления файлов в общей папке: обычно удалить может владелец файла, владелец папки или администратор.

Пример: Часто применяется к /tmp; не заменяет обычные права rwx.

### Запуск через сокет / socket activation

Система сначала слушает точку входа и при обращении запускает нужную службу.

Пример: В Ubuntu SSH может принимать новые соединения через ssh.socket; inactive у ssh.service не всегда означает недоступность SSH.

### Кластер PostgreSQL

В контексте пакетов Ubuntu — экземпляр PostgreSQL с набором баз и конфигурацией. Это не обязательно несколько компьютеров.

Пример: pg_lsclusters показывает локальные экземпляры, их версии, порты и состояние.

### SQL

Язык запросов и изменений данных в реляционной базе.

Пример: SELECT читает строки, INSERT добавляет, CREATE TABLE создаёт таблицу.

### Выгрузка / dump

Копия данных в формате штатного инструмента базы.

Пример: pg_dump сохраняет одну базу, pg_restore возвращает выгрузку custom-формата.

### Upstream / внутреннее приложение

Обработчик, к которому прокси отправляет запрос дальше.

Пример: Для нашего Nginx upstream — Python на 127.0.0.1:8000.

### ACME

Протокол автоматического получения и продления TLS-сертификатов с проверкой права управлять именем.

Пример: Certbot может подтвердить настоящий домен и настроить сертификат; .test для публичного сертификата не подходит.

### Кеш

Временное хранилище, из которого можно быстрее получить уже подготовленные данные.

Пример: Кеш можно пересоздать, если точно известно его назначение; база и единственная копия документов кешем не являются.

### Сетевой backend / renderer

Компонент, которому Netplan передаёт применение сетевых настроек.

Пример: networkd и NetworkManager — разные варианты; существующий вариант не меняют без причины.
